## A. 技术选型名词

### 体素（Voxel）

- 一句话定义：把三维空间切成规则小立方体来表示世界，可类比"3D 像素"。
- 在本项目里是什么 / 为什么需要：世界由体素堆成，可放置与破坏。选它的根本理由是**规则网格**——能用数组存、能用整数坐标寻址，因此能比任意几何体做激进得多的优化。
- 易错点或关键取舍：别把"体素"等同于"方块游戏"。体素是**数据结构选择**，方块外观只是它的表现。

### 区块（Chunk）

- 一句话定义：世界的固定大小切片，是**加载 / 渲染 / 存储的最小单位**。
- 在本项目里是什么 / 为什么需要：本方案为 16×384×16。流式加载、脏标记、序列化全部以区块为单位。
- 易错点或关键取舍：区块是**数据归属单位**，不是渲染单位，也不该是锁单位。

### Section（子区块 / 垂直分段）

- 一句话定义：区块在垂直方向再切成的 16³ 小段（16×384×16 → 24 个 Section）。
- 在本项目里是什么 / 为什么需要：全空气的 Section 可以**不存、不网格化、不上传**，省下大量内存与带宽。
- 易错点或关键取舍：贪婪网格化的作用域**只到单个 Section**（顶点位置用 uint8 存 0~16）。

### 调色板压缩（Palette）+ 位打包

- 一句话定义：一个 Section 内通常只有少数几种方块，于是存一张"去重后的方块 ID 列表"（调色板），每个方块只存调色板下标，位数按调色板大小动态决定（4~8 bit）。
- 在本项目里是什么 / 为什么需要：把每方块 4 字节压到 0.5~1 字节，是单区块内存降到 8~20 KB 的关键。
- 易错点或关键取舍：调色板变化时需重新打包；读方块多一层间接寻址。

### 面剔除（Face Culling）

- 一句话定义：只为"邻居是空气或透明方块"的那些面生成几何。
- 在本项目里是什么 / 为什么需要：地下实心区域内部的面对面玩家不可见。效果是把单区块面数从最高 6 万降到几百~几千。
- 易错点或关键取舍：**必须跨区块取邻居方块**——区块边界面的可见性依赖邻居数据。

### 贪婪网格化（Greedy Meshing）

- 一句话定义：把同材质、同朝向、同光照的相邻面**合并成一个大四边形**。
- 在本项目里是什么 / 为什么需要：在面剔除基础上再压 3~10 倍。
- 易错点或关键取舍：① 作用域只到单 Section；② 合并判据必须含 4 个角的**光照与 AO**（AO 是逐顶点量，不同就不能合）。

### 视锥剔除 / 遮挡剔除

- 一句话定义：视锥剔除 = 跳过相机视野外的区块；遮挡剔除 = 跳过**被其它几何挡住**的区块。
- 在本项目里是什么 / 为什么需要：视距越大越必要；洞穴场景尤其依赖遮挡剔除。
- 易错点或关键取舍：视锥剔除便宜、遮挡剔除昂贵，后者要谨慎实现并配 Tracy 数据。

### 纹理图集（Atlas）vs 纹理数组（Texture Array）

- 一句话定义：图集是把所有纹理拼成一张大图；数组是每张纹理独立成"一层"，采样时用层号索引。
- 在本项目里是什么 / 为什么需要：**本项目选数组**。图集在开启 mipmap 时相邻 tile 会互相**渗色**（低级别 mip 把邻居颜色混进来），需要留 gutter 补丁；数组天然没有这个接缝问题。
- 相关：ADR 0001、`references/meshing-and-render.md`

### Draw Call

- 一句话定义：CPU 向 GPU 提交一次绘制命令。
- 在本项目里是什么 / 为什么需要：每次提交都有开销，数量过多时 CPU 成为瓶颈。目标 ≤700/帧 @16 区块、≤1500/帧 @24 区块。
- 易错点或关键取舍：压缩它靠**合并网格**，不是减少三角形数量。

### LOD / Impostor

- 一句话定义：LOD = 远处区块用低精度网格；Impostor = 超远距离直接用一张贴图替代实体方块。
- 易错点或关键取舍：相邻不同 LOD 之间会出现**裂缝**，需要缝合策略。

### 噪声：Perlin / Simplex / Worley

- 一句话定义：给定坐标返回连续随机值的函数，用来程序化生成地形。
- 在本项目里是什么 / 为什么需要：2D 噪声叠成高度图；3D 噪声挖洞穴；2D 温度 + 湿度映射生物群系。库选 **FastNoiseLite**（轻量 header-only）。
- 易错点或关键取舍：它是 **float 实现** → 只能保证"同一构建内确定性"，跨编译器 / 平台可能有差异。

### 网格抖动（Chunked Jittered Grid）vs 泊松盘采样（Poisson Disk）

- 一句话定义：网格抖动 = 把世界切成格子、每格按种子随机放一个点；泊松盘 = 保证任意两点有最小距离。
- 在本项目里是什么 / 为什么需要：**本项目选网格抖动**。泊松盘观感更自然，但需要**全局激活点列表**，与"走到哪生成到哪"的流式分块根本冲突——它做不到"只看当前区块即可重建"。
- 相关：`references/chunk-and-streaming.md`

### 天空光 / 方块光 / BFS 传播

- 一句话定义：天空光从世界顶部向下传播、遇不透明方块停止；方块光（火把、岩浆）向四周传播、每格衰减 1 级；两者都用广度优先（BFS）逐格扩散。
- 在本项目里是什么 / 为什么需要：必须**增量更新**——只在区块加载或方块改动时传播变化部分，不能每帧全场景重算。
- 易错点或关键取舍：光会**跨越区块边界**传播；邻居加载 / 卸载时须能越界重传，否则出现黑边。

### AO（环境光遮蔽，Ambient Occlusion）

- 一句话定义：角落因被邻接方块遮挡而自然变暗。
- 在本项目里是什么 / 为什么需要：原版 MC 的观感很大一部分来自它，成本低、收益大。
- 易错点或关键取舍：**逐顶点量**，会破坏贪婪合并的等价条件，因此合并判据必须包含它。

### swept AABB / 子步进（Sub-stepping）/ 自动上台阶

- 一句话定义：swept AABB 把移动视为一段位移、检测它与方块 AABB 的**扫掠相交**；子步进把每帧位移拆成若干小步推进；自动上台阶在遇到 1 格坎时自动抬升。
- 在本项目里是什么 / 为什么需要：只为玩家包围盒周围 **3×3×3 个方块**做查询，是纯整数索引，比通用物理引擎快上百倍。
- 易错点或关键取舍：不要靠"把碰撞盒缩小 20%"改善手感——那会让玩家看起来悬空，且能从缝隙掉下去。

### 固定时间步长（Fixed Timestep）

- 一句话定义：逻辑与物理用恒定的 dt 更新，渲染侧做插值。
- 在本项目里是什么 / 为什么需要：可变 dt 会让物理行为随帧率变化，直接破坏确定性。

### 相机相对渲染（Origin Rebasing）

- 一句话定义：世界坐标用整数（int32 / int64），渲染时把"世界原点"动态搬到相机附近。
- 在本项目里是什么 / 为什么需要：float 只有 24 位有效位，离原点约 2²⁴ 格后精度不足 1 格，画面会抖。
- 易错点或关键取舍：所有位置一律整数，float 只用于渲染与插值等相对量。

### Job System / 依赖计数 / DAG

- 一句话定义：能表达任务间依赖关系的调度器。
- 在本项目里是什么 / 为什么需要：异步区块管线是一张**有依赖的图**（生成 → 邻居就绪 → 光照 → 网格化 → 上传），朴素线程池表达不了"等 4 个邻居都完成再网格化"。**本项目已采用 enkits**（vcpkg 端口名 `enkits`，注意无连字符）；备选 Taskflow 与自研无锁池的取舍见 ADR 0003。

### ECS（Entity-Component-System）

- 一句话定义：用"实体 + 组件 + 系统"组合代替继承的数据驱动架构。
- 在本项目里是什么 / 为什么需要：**体素场景里 ECS 只服务少量动态实体**（怪物、掉落物）。方块不是 Entity，区块顶多算一个。
- 易错点或关键取舍：别把 ECS 当性能银弹，它不是体素性能的主要杠杆。
- 本项目实现：**EnTT**（vcpkg 端口 `entt`，起步）；自研稀疏集为备选，切换条件见 ADR 0003。

### RHI（Render Hardware Interface）

- 一句话定义：把不同图形 API（Vulkan / D3D12 / Metal）包成统一接口。
- 在本项目里是什么 / 为什么需要：选 **SDL3_gpu** 直接充当这一层，避免自己写多后端。
- 易错点或关键取舍：抽象不能泄漏某个 API 的语义，否则换后端就返工。

### SPIR-V / DXIL / GLSL / HLSL

- 一句话定义：GLSL / HLSL 是人写的高级着色器语言；SPIR-V 是 Vulkan 用的中间字节码；DXIL 是 D3D12 用的字节码。
- 在本项目里是什么 / 为什么需要：**Shader 格式与渲染后端强耦合**——Vulkan 只吃 SPIR-V，D3D12 只吃 DXIL。所以构建期同时产出两种，运行时按设备能力选。
- 相关：本文件 D 区「双格式 Shader 管线」

### 区域文件（Region File）

- 一句话定义：把 32×32 个区块合并存进一个文件（如原版 MC 的 `.mca`）。
- 在本项目里是什么 / 为什么需要：避免"每区块一个小文件"造成文件数爆炸与读放大。本项目格式为 `.voxr`。

### zstd

- 一句话定义：现代高速压缩库。
- 在本项目里是什么 / 为什么需要：区块二进制存档要体积小、解压快；比 gzip 更快、比 LZ4 压得更狠。

### 单写者 + 不可变快照

- 一句话定义：一个区块同时只由一个 Worker 构建，构建完成后整体替换指针发布，主线程只读已发布版本。
- 在本项目里是什么 / 为什么需要：避免对区块加粗粒度锁——那会把主线程拖垮。
- 易错点或关键取舍：不能让主线程"边构建边读"。

### MDI（Multi-Draw Indirect）

- 一句话定义：一次命令提交多组绘制（绘制参数放缓冲区间接寻址），大幅削减 CPU 提交开销。
- 在本项目里是什么 / 为什么需要：**备选方案**，仅在确实需要把 Draw Call 压到"几百"时才启用。

### LFS（Git Large File Storage）

- 一句话定义：Git 的大文件扩展——仓库里存指针文件，实体另存。
- 在本项目里是什么 / 为什么需要：`.gitattributes` 已为 png / jpg / ogg / wav / fbx / glb 声明 LFS。

### 分层混合世界（Layered Hybrid World）

- 一句话定义：把"世界"拆成几层不同的表示，各管一段，而不是用**一种**表示硬扛全部需求。
- 在本项目里是什么 / 为什么需要：**本项目采用**（见 [ADR 0004](adr/0004-hybrid-layered-world-representation.md)）——① 高度场地表 ② 可挖标记区域内的有界 SDF 体积 ③ 物件/建造层 ④ 实体。选它的理由是"全世界三维体素"虽能力最强，但数据量约为高度场的 34 倍、网格化遍历量高两个数量级，而"全世界任意三维重塑"**并不是需求**。
- 易错点或关键取舍：**浮空物与建造物绝不能写进地形场**（会在地表打出柱子）；层与层的交界处（洞口、天坑）必须共享采样或做过渡，否则出现裂缝与穿模。

### 高度场（Heightfield）

- 一句话定义：用"每个水平格子一个高度值"表示地形（2.5D），表面由三角网格平滑渲染。
- 在本项目里是什么 / 为什么需要：地表的表示。数据量极小（32×32 单位约 4 KB），挖坑/堆土/平整就是改高度值；LOD 有成熟工业方案（Geometry Clipmaps、CDLOD），这是它相对体素的最大优势。
- 易错点或关键取舍：**不能表达悬垂、洞穴、隧道**（每列只有一个高度）。所以洞穴与地下三维挖掘必须交给 ② 的可挖体积。

### 有符号距离场（SDF）与等值面网格化

- 一句话定义：SDF = 每个三维格点存"到表面的带符号距离"（负=内部、正=外部、0=表面）；等值面网格化（Marching Cubes 系）把这张场抽成三角网格，因此**数据是格子、看到的却是平滑曲面**。
- 在本项目里是什么 / 为什么需要：可挖体积的表示。它正是"代码层面一个个格子、玩家看到平滑表面"的实现方式。
- 易错点或关键取舍：① 三种算法的取舍——**Surface Nets**（每格最多 1 顶点、顶点连续变化，LOD 过渡天然平滑，实现最简）／**Marching Cubes**（最成熟但顶点位置会跳变，LOD 缝合难）／**Dual Contouring**（能保留锐利棱角，需 QEF 求解）；② 密度精度（8 bit 省一半内存，但陡坡会出现台阶感与 alias）；③ 网格化作用域必须分块，且相邻块要共享边界采样，否则出现接缝。

### 多纹理权重混合（Splat Map）

- 一句话定义：地表不贴单张纹理，而是按"高度 / 坡度 / 生物群系"算出多种纹理的混合权重，在着色器里加权混合。
- 在本项目里是什么 / 为什么需要：替代方块世界的"纹理数组 + 层号"方案；陡坡露岩、平地草土过渡，都靠它。
- 易错点或关键取舍：权重必须归一化，否则亮度随层数漂移；纹理层数要按硬件采样上限控制。
- 本项目现状（[ADR 0009](adr/0009-terrain-material-pipeline.md)）：权重在**片元着色器逐像素**算（不再写进顶点属性，见下一条），过渡带用**窄带 `smoothstep`**；每层带 albedo + 法线贴图与各自的 UV 尺度；参数全部由 `assets/config/materials.toml` 经 `BuildMaterialUniform` 投影，**CPU / GPU 同源**。

### MSAA（多重采样抗锯齿）与 resolve；RNM 细节法线

- 一句话定义：**MSAA** 让每个像素保留多个几何采样点，只在**几何边缘**上做超采样，再在渲染目标上"解析（resolve）"成单采样结果；**RNM（Reoriented Normal Mapping）** 是把两层法线贴图合成的常用做法，比简单相加更不容易"压平"细节。
- 在本项目里是什么 / 为什么需要：**MSAA 治"边缘锯齿 + 远处地形闪烁"**——这是"看起来旧"的一大来源。本项目在 P3 落地：主通道渲进 `R16G16B16A16_FLOAT` **多采样目标**，再 resolve 到单采样 HDR 目标（色调映射读后者）；**档位进 `settings.toml`（1/2/4/8）**，档位 = 1 时**不创建多采样纹理**（零额外开销）。RNM 用于把**第二频段**的高频细节法线叠到基础法线上，让近景更"细腻"。
- 易错点或关键取舍：① **resolve 用 `SDL_GPU_STOREOP_RESOLVE`，不要用 `RESOLVE_AND_STORE`**——多采样内容此后不再被采样，保留它纯属浪费带宽（`SDL_gpu.h` 明说后者"需要可观的显存带宽"）；② **管线与渲染目标的采样数必须严格一致**，故 MSAA 档位变化要**重建管线**（本项目因此把 Shader 持有到析构，而不是建完管线就释放）；③ **阴影通道保持 1×**（它本来就只写深度，且随后是手动 PCF，开 MSAA 只增开销），深度目标**不需要 resolve**（`SDL_gpu.h`：深度/模板目标不支持多采样解析）；④ **显存很贵**：4× 在 1080p 约 95 MB（颜色 63 + 深度 32），是"看不见的基础设施"里最贵的一块——预算吃紧时先降档位而不是先降材质；⑤ 细节法线的第二频段**只对权重最高的一层做**，否则每层多一次采样、带宽成倍上涨（§7.2.2 里材质采样本就是最大一笔）。
- 相关：[ADR 0010](adr/0010-render-quality-pipeline.md) P3 与「修订说明」、方案 §7.2.1 / §7.2.2、`engine/render/mesh_renderer.*`、`assets/shaders/mesh.frag`

### PBR（Physically Based Rendering）与"四件套"

- 一句话定义：用**物理化的反射模型**（而不是"环境项 + 漫反射"两盏常数）描述表面，输入是 **albedo / normal / roughness / AO** 四张贴图（通常再加 metallic，本项目地表是电介质、**不引入 metallic**）。本项目用 **Cook-Torrance**：法线分布 **GGX(D)** + 几何项 **Smith(G)** + 菲涅尔 **Schlick(F)**，电介质 `F0 = 0.04`。
- 在本项目里是什么 / 为什么需要：它是"纸板感"与"有材质感"的分界线——**没有镜面项，岩石和沙地在数学上是同一种材质**，只能靠颜色区分。有了 roughness 贴图，岩石可以又硬又亮、沙地依旧哑光。
- 易错点或关键取舍：① **AO 只作用于环境项**（天空光），不作用于直接光——否则会把受光面也压黑；② 粗糙度要**钳制下限**，`α = roughness²` 接近 0 时高光会出现除零 / 硬点；③ 四件套意味着**每层多 3~5 次采样**，必须沿用 ADR 0009 那条"**只采权重最高的 3~4 层**、近零权重直接跳过"的守卫，否则带宽会成倍上涨（§7.2.2 里材质采样本来就是最大的一笔）；④ 漫反射的 `1/π` 归一化口径要想清楚——本项目把它折进光照强度常量，以保持与 P1 的亮度对齐、避免重新校准 `lighting.toml`（这一条写在 `mesh.frag` 顶部注释里）。
- 相关：[ADR 0010](adr/0010-render-quality-pipeline.md) P2、`assets/shaders/mesh.frag`、`world/terrain/material_table.*`、`assets/config/materials.toml`（`schema_version = 3`）

### 逐像素权重 vs 逐顶点权重（材质过渡带宽）

- 一句话定义：材质混合权重是"在顶点上算好让 GPU 插值"，还是"在片元里按世界坐标/法线重算"。
- 在本项目里是什么 / 为什么需要：本项目曾用**逐顶点**权重，结果大棱角处出现**大片过渡色带**——一个三角形内坡度从缓变陡，整段变化被线性插值摊在约 1 格宽（≈ 一个人高）里。改为**逐像素**重算后，过渡带宽只由配置里的 `height_blend` / `slope_blend` 决定，**与顶点间距解耦**：不加顶点、不涨显存。
- 易错点或关键取舍：① 逐顶点插值的问题在于"整段变化被摊在一个三角形里"，**加密顶点只能让带变窄、不能消除**（顶点间距是放大器，不是根因）；② 逐像素重算本身很便宜（几次点乘 + `smoothstep`），前提是片元里能拿到**世界坐标**——本项目靠 uniform 里的"渲染原点"+ 相机相对顶点坐标还原（红线 6）；③ 两边公式必须逐字镜像（本项目抽了 `MaterialBandFactor` 供 CPU 复用），否则 CPU 判据与画面不符。

### 贴图不是"省性能"手段：采样带宽才是开销

- 一句话定义：用贴图表现细节（而不是用几何 / 顶点色）**增加**开销，它买到的是"外观"，不是"性能"。
- 在本项目里是什么 / 为什么需要：用户曾问"直接渲染性能开销太大，是不是该改用贴图"。实际相反——逐像素算权重很便宜，**昂贵的是每层贴图的采样次数**（4 层 × albedo + 法线 = 8 次带各向异性过滤的采样）。
- 易错点或关键取舍：性能旋钮是**采样层数 / 分辨率 / 各向异性等级**，不是"少用贴图"。本项目据此定了"只采权重最高的 3~4 层 + 近零权重直接跳过采样（`kWeightEpsilon`）"；再要压采样数就要上 RVT / 虚拟纹理（ADR 0009 的切换条件）。

### HDR、色调映射（Tone Mapping）与 sRGB 编码

- 一句话定义：**HDR** = 渲染时允许颜色值超过 1（用浮点目标存）；**色调映射** = 把这段超范围的亮度"压"回 [0,1] 且不硬截断；**sRGB 编码** = 把线性亮度转成人眼友好的显示编码。
- 在本项目里是什么 / 为什么需要：这三件事一起解决"画面**发灰、发脏、没有动态范围**"。本项目此前**一个都没有**（全仓库检索 `sRGB` / `gamma` / `tonemap` / `exposure` 曾零命中），着色器算出的值直接写进 UNORM 交换链 ⇒ 亮部一过 1.0 就死白。现状（ADR 0010 P0）：主通道渲到 `R16G16B16A16_FLOAT` 离屏目标 → `tonemap.frag` 做 曝光 → ACES 近似 → 分段精确 sRGB 编码 → 交换链。
- 易错点或关键取舍：① **颜色要在正确的空间里算**——作者给的 `tint` 是 sRGB 观感值，必须先转线性再参与光照，最后再编码回 sRGB；中间漏一步就会整体偏白或偏暗。② 色调映射一上，**既有的颜色常量都要重新校准**（属预期返工）。③ 曝光是**参数不是魔法**：进配置文件，才能不重编 Shader 就能调。
- 相关：[ADR 0010](adr/0010-render-quality-pipeline.md)、`assets/shaders/tonemap.frag`、`engine/platform/settings.*`（`exposure`）

### 半球天空光（Hemispheric Sky Light）与指数高度雾（Exponential Height Fog）

- 一句话定义：**半球天空光** = 用一个"上方天空色 ↔ 下方地面反弹色"的梯度当作环境光，按法线朝向插值；**指数高度雾** = 让颜色随视距按指数衰减地混向雾色（并随高度差衰减）。
- 在本项目里是什么 / 为什么需要：这两件是"3A 观感"里**性价比最高的环境与纵深**。天空光解决"**背光面死黑**"（只用一盏方向光时，背光面几乎全黑，物体像剪纸）；雾解决"**远景硬边、没有纵深**"（远处几何高频还会闪烁）。二者在本项目都已进 `assets/config/lighting.toml`，改参数**不需重编 Shader**。
- 易错点或关键取舍：① 天空光强度不能照搬物理比值（环境约为直射的 1/10）——在色调映射前会压到接近 0，本项目取与太阳同量级的强度，实测背光感知亮度落在 0.13~0.32（不死黑）；② 雾**必须在线性空间、光照之后、色调映射之前**施加，且雾色默认取天空地平色，否则地平线会出现色带硬边；③ 雾的公式要写明量纲（本项目 `density` 为 1/格、`height_falloff` 为 1/格），否则调参没有手感；④ `enabled=false` 时应整段跳过，不留无用运算。
- 相关：[ADR 0010](adr/0010-render-quality-pipeline.md)、`assets/config/lighting.toml`、`engine/render/lighting_table.hpp`、`assets/shaders/mesh.frag`

### 显存与带宽记账（为什么"达标"要有可核对的数字）

- 一句话定义：把 GPU 资源占用（显存）与每帧数据搬运量（带宽）**按项算清楚并写进预算表**，而不是凭印象说"应该够用"。
- 在本项目里是什么 / 为什么需要：ADR 0010 引入渲染质量线后，必须回答"这些新目标会不会挤爆 VRAM"。做法分两层：① **运行期记账**——纹理与渲染目标在创建 / 释放时增减 `RenderStats::textureBytes`，并在启动日志按项打印（实测 1280×720：材质 2.67 + 深度 3.52 + HDR 7.03 = 13.21 MB）；② **预算表**——方案 §7.2.1 / §7.2.2 列出当前各项与 P1/P3 的增量预估。
- 易错点或关键取舍：① 纹理数组的 mip 链各级面积收敛到第 0 级的 **4/3**（几何级数），漏掉这一项会低估 33%；② 分辨率的字节宽差异很大——`R8G8B8A8` 与 `D32_FLOAT` 是 4 B/px、`R16G16B16A16_FLOAT` 是 8 B/px，MSAA 还要再乘采样数；③ **带宽的账和显存的账是两件事**：本项目里 HDR 通路每帧只约 33 MB，而材质采样在最坏情况下约 253 MB/帧——**瓶颈在采样，不在渲染目标**；④ 记账值与驱动实际占用有差异（对齐、驱动内部开销），故保留 RenderDoc 交叉核对。
- 相关：方案 §7.2.1 / §7.2.2、[ADR 0010](adr/0010-render-quality-pipeline.md)、`engine/render/mesh_renderer.hpp`（`RenderStats`）

### SDL_gpu 的坐标约定（NDC 与纹理坐标的 Y 方向**相反**）

- 一句话定义：SDL_gpu 的**裁剪空间**是"左下角 `(-1,-1)`、右上角 `(1,1)`"（**+Y 向上**，Z 取 `[0,1]`）；而**纹理坐标**是"左上角 `(0,0)`、右下角 `(1,1)`"（**+Y 向下**）。视口坐标也是"左上角 `(0,0)`、+Y 向下"。
- 在本项目里是什么 / 为什么需要：**全屏后处理通道**（如色调映射）必须做 V 翻转：`uv = vec2(pos.x*0.5+0.5, 0.5 - pos.y*0.5)`。本项目 P0 第一版照直写了 `pos*0.5+0.5`，结果屏幕上方取到图像底部 ⇒ **整帧上下翻转**；又因为 ImGui 叠加层是在后处理**之后**直接写交换链的，症状是"**UI 正常、世界倒置**"（缺陷 B5）。
- 易错点或关键取舍：① 后端差异（Vulkan 的 NDC 本身是 +Y 向下）**由 SDL 自动转换**，所以**不要**在 shader 里额外翻转；② 三大坐标空间（NDC / 视口 / 纹理）的 Y 方向**不统一**，凭直觉写全屏三角形极易踩坑；③ 权威依据是本机头文件 `SDL_gpu.h` §Coordinate System，**先查再写**。
- 相关：`assets/shaders/tonemap.vert`、`references/meshing-and-render.md` §4、[devlog](devlog.md) 2026-09-26 B5 记录

### 级联阴影贴图（CSM，Cascaded Shadow Maps）

- 一句话定义：把相机视锥按距离切成若干段，每段用一张分辨率合适的阴影贴图，让近处清晰、远处不糊。
- 在本项目里是什么 / 为什么需要：替代方块世界的"天空光/方块光 BFS 逐格传播"。平滑大世界 + 方向光必须靠 CSM，否则阴影要么糊要么开销爆炸。
- 易错点或关键取舍：级联之间会有缝合缝与闪烁，需要随相机做 texel 对齐。
- 本项目现状（[ADR 0010](adr/0010-render-quality-pipeline.md) P1 第二步）：3 级 × 2048² `D32_FLOAT` **深度数组**（48 MB），**texel 对齐**的光空间矩阵（纯函数 `engine/render/shadow_cascade.*`，有单测钉死"亚 texel 平移不改变矩阵"），片元侧**按视轴线性深度选级** + **3×3 手动 PCF** + 几何法线偏移抗 acne；剔除策略是 **BACK**（地表是单面高度场外壳，若剔除 FRONT 会让受光面完全不写深度、阴影图空白）。级联分割、覆盖距离、偏移量全部进 `lighting.toml [shadow]`。
- 又一条易错点：**深度通道也必须处理"相机相对顶点"**——主通道顶点已减去渲染原点，阴影通道复用同一批顶点缓冲，故光空间矩阵必须在渲染原点坐标系下构造（等价于世界空间矩阵右乘 `translate(-renderOrigin)`），否则阴影整体错位。

### 阴影投射体扩展（Shadow Caster Extension）

- 一句话定义：级联阴影的光空间正交盒通常按"相机视锥切片"拟合，但**还必须在朝太阳的方向上向后延伸、并在横向加宽**，才能把"比切片还高的投射体"（高塔、山尖、飞在空中的物件）包进去。
- 在本项目里是什么 / 为什么需要：不做这一步时，**高柱子的顶部会被阴影通道裁掉**（X/Y 出盒 + `enable_depth_clip` 把沿光轴超范围的部分剪掉），于是只有"落在盒内的那段塔身"参与投射；相机一动，切片变、盒变，**参与投射的塔身段就变了 ⇒ 阴影随视角变化**（缺陷 B6）。修法是沿光轴远端前移 `casterHeight / |dir.y|`、X/Y 各扩 `casterHeight · tanθ`（θ = 光照方向与竖直的夹角），`casterHeight` 取 **最高地表高度 − 该级切片中心高度**（每级独立算，本项目由 `TerrainWorld::MaxSurfaceHeightBlocks()` 自动推导 + 配置下限兜底）。
- 易错点或关键取舍：① **坐标系一致性**——级联中心是"渲染原点相对"坐标，投射体高度也必须换算到同一坐标系，否则扩展量偏移（本项目靠"两者都减渲染原点"自然抵消，已在注释写明）；② **代价是分辨率摊薄**：盒越大，同样的 2048² 阴影图覆盖的地面越多、每 texel 越粗；③ 太阳接近地平线时 `|dir.y| → 0` 会让扩展量爆炸，必须钳制（本项目取 `eps = 0.05`）。
- 相关：`engine/render/shadow_cascade.*`、`assets/config/lighting.toml [shadow].caster_height_min`、缺陷 B6 的 devlog 记录

### 材质带（高度 / 坡度）的"覆盖不变量"

- 一句话定义：材质混合的**归属函数**（每层 = 高度带隶属度 × 坡度带隶属度）必须有"**覆盖完整**"这条不变量 —— 任意 `(高度, 坡度)` 至少有一层权重非零。
- 在本项目里是什么 / 为什么需要：不满足时，权重全为 0 会**落到"无匹配 → 槽位 0"的兜底分支**。本项目就踩过：`materials.toml` 的带在**高度 120、坡度 0** 处四层全 0，于是**整片平台被强制涂成槽位 0（草）的颜色**，而真实原因被"看起来是绿的"掩盖了很久（缺陷 B7）。现在这条不变量有**单测**（在 `高度 ∈ [0,512] × 坡度 ∈ [0,1]` 的网格上断言覆盖量 > 阈值），兜底分支也加了警示注释。
- 易错点或关键取舍：① **兜底分支不能当"正常路径"用**——它存在是为了"权重非负且和为 1"的数学完备性，触发即意味着配置有洞；② 带之间必须**有交叠**（某个高度上 `草` 的下降段要与 `土` 的上升段重叠），否则按 16 格步长扫就会漏；③ 参数字面很好改，但**改一处就可能开洞**——本项目在 `materials.toml` 文件头写明了"最容易被改坏的一条"并给出覆盖论证；④ "高海拔平地呈岩"与"低坡度不出现岩"在**乘积模型**下不可兼得（岩的坡度带若包含 0，就会同时把平地涂成灰绿）——必须显式取舍并留档。
- 相关：`assets/config/materials.toml`（文件头覆盖论证）、`world/terrain/material_blender.*`、缺陷 B7 的 devlog 记录

## B. 开发流程与工程用语

### PoC（Proof of Concept，概念验证）

- 一句话定义：正式开发前，用**最小、可丢弃**的实验回答"某个关键假设是否成立"。
- 在本项目里是什么 / 为什么需要：有些假设错了就要改架构，代价极大。本项目 #1 验证 SDL3_gpu 后端可用性、#2 验证 Shader 工具链格式——**正是 #2 推翻了"只编 SPIR-V"的假设**。
- 易错点或关键取舍：PoC 的目的是**回答问题**，不是交付功能；允许粗糙、用完即弃。
- 相关：[devlog.md](devlog.md) 2026-09-25 第 5 条

### CI（Continuous Integration，持续集成）

- 一句话定义：每次推送代码，服务器**自动**跑一遍"检查 → 构建 → 测试"，用红 / 绿灯反馈。
- 在本项目里是什么 / 为什么需要：`.github/workflows/ci.yml`，三步：门禁 → 构建（Win Debug/Release + Linux ASAN/TSan）→ 测试；红灯不合并。
- 易错点或关键取舍：本地环境没装齐时，CI 往往是**唯一**的验证通道。

### 门禁（Gate）

- 一句话定义：用机器执行的**规范检查**，通常作为 CI 第一步，失败即终止。
- 在本项目里是什么 / 为什么需要：`check-banned-identifiers.ps1` 扫描源码里被禁的写法。它把"禁止项"从"依赖人记住"变成"构建直接失败"。

### DoD（Definition of Done，完成定义）

- 一句话定义：一个任务算"做完"的检查清单。
- 在本项目里是什么 / 为什么需要：开发规范第七节的 15 项自检。

### 阶段计划（Plan）

- 一句话定义：一份写清"这个阶段做哪些任务、按什么顺序、做到什么算完、现在到哪了"的活文档。
- 在本项目里是什么 / 为什么需要：放在 `docs/plans/<阶段>.md`（如 `docs/plans/v0.1.md`），是**第 4 份常驻文档**，也是交接包的第 3 份。规范要求「任何一次任务下发，动手前必须先把任务写进计划（范围 / 顺序 / 落点 / 验收）」，目的是让接手者（人或大模型）**只读这一份文件就能开工**，不必靠反推 devlog 猜下一步。
- 易错点或关键取舍：① 它是**活文档**，每完成一步就要勾选并更新「当前进度 / 下一步」，与代码**同一次提交**；② 它**不写技术结论**，选型与理由只引用方案 / ADR，否则又造出第二个事实来源；③ 阶段闭环后**冻结不回改**，新阶段新建文件；④ 「下一步」必须可执行、可验收，写"继续优化"等于没写。
- 相关：`SKILL.md` 第六.4 节与「任务下发」一节、`docs/plans/v0.1.md`

### 决策索引（ADR Index）与方案版本取代

- 一句话定义：`docs/adr/README.md` 是一张"**哪些决策还生效**"的总表；方案文档换版时，旧版必须显式声明被取代的范围。

### vcpkg host 依赖（`"host": true`）

- 一句话定义：把某个依赖标记为"只在**构建机**上需要"，vcpkg 用 host triplet 构建它，并把它提供的可执行工具暴露给构建系统。
- 在本项目里是什么 / 为什么需要：`glslc`（`shaderc` 端口）与 `shadercross`（`sdl3-shadercross` 端口）是**构建期工具**，不是链接进产物的库。写成 `{ "name": "shaderc", "host": true }` 后，`cmake/Shaders.cmake` 的 `find_program` 能找到它们，开发机与 CI 都不必手工配 `PATH`。
- 易错点或关键取舍：写成普通字符串（`"shaderc"`）会被当作**目标平台库**处理，不保证工具可见。另：host 依赖会传递地带出其依赖的特性——`sdl3-shadercross` 会拉入 `sdl3[vulkan]`、`directx-dxc`、`glslang`、`spirv-cross`，首次 configure 明显变慢（不是卡住）。
- 相关：`vcpkg.json`、`cmake/Shaders.cmake`、`references/build-and-tests.md` §1

- 一句话定义：把编译警告当错误处理，任何警告都让构建失败。
- 在本项目里是什么 / 为什么需要：C++ 的警告常是真 bug 的预兆，攒着只会越来越多。

- 一句话定义：原本正常的功能因新改动而坏掉。
- 在本项目里是什么 / 为什么需要：CI + 单元测试的主要目的就是拦住它。

- 一句话定义：同样的输入必然得到同样的输出。
- 在本项目里是什么 / 为什么需要：分**两级**——「同一构建内确定性」（单机可依赖）与「跨平台确定性」（联机 / 共享种子才需要，须改用整数哈希噪声）。

## D. 本项目专属概念

### 区块状态机与跨区块唯一判据

> ⚠ **已被 ADR 0004 取代（迁移期）**：本条目描述的是方块世界下的"区块 / Section"状态机，其尺寸常量与判据载体
> 随世界表示改为**分层混合**而作废。**"邻居就绪才可网格化"这一原则仍然成立**，但作用域将改为
> 「地表 tile / 可挖体积块」——详见 [ADR 0004](adr/0004-hybrid-layered-world-representation.md)。

- **一句话定义**：给每个区块贴一个"走到哪一步了"的标签，并规定"满足什么条件才允许开始算网格"。
- **在本项目里是什么 / 为什么需要**：
  - 状态**只能单向推进，不得跳级**：`Empty → Generating → Generated → Lit → Meshed → Ready`
  - `Empty` 占位 → `Generating` 后台填方块 → `Generated` 方块就绪（邻居可查询）→ `Lit` 光照完成（含跨边界）→ `Meshed` 要画的面算完 → `Ready` 已上传 GPU，可渲染与碰撞查询。
  - **唯一判据 `can_build_mesh`**（`voxel/chunk/chunk_types.hpp`）：**自身 ≥ `Generated`，且 4 个水平邻居均 ≥ `Lit`**，才允许进入 `Meshed`。
  - 为什么必须等邻居：**一个面要不要画，取决于邻居方块是什么**。区块边界处邻居未就绪时，面剔除判断不完整，视觉上就是边界上一条闪烁的裂缝。
  - 为什么强调"唯一"：条件若散落在十几处代码里各写一遍，早晚有人写漏一处，且极难排查。收进一个函数即**单一事实来源**，所有网格化路径都必须经过它，不得绕过。
- **易错点或关键取舍**：
  - 光照也必须跨边界，不只是网格；邻居加载 / 卸载时要能重新传播，否则出现黑边。
  - **"邻居中途卸载"是最容易被遗漏的情形。**
  - 自身处于 `Empty` / `Generating` 时绝不能开始网格化。
- **相关**：`references/chunk-and-streaming.md`（§2 状态机、§3 邻居依赖）、`tests/chunk_state_test.cpp`

### 双格式 Shader 管线

- **一句话定义**：同一份 GLSL 源码在**构建期产出两种**字节码（SPIR-V 与 DXIL），运行时按当前图形后端加载对应的那一种。
- **在本项目里是什么 / 为什么需要**：
  - Shader = 跑在显卡上的小程序（本项目用 GLSL 写）。**Shader 格式与图形后端强耦合**：Vulkan 只接受 SPIR-V，Direct3D 12 只接受 DXIL，喂错直接崩溃。
  - 而 SDL3_gpu 会自动挑选后端（**Windows 上默认 D3D12**，有可用 Vulkan 的机器才走 Vulkan），因此只备一种格式必然有一类机器跑不起来。
  - 链路为**两段式**：`triangle.vert (GLSL) --glslc--> .spv (SPIR-V) --shadercross--> .dxil (DXIL)`
  - 运行时用 `SDL_GetGPUShaderFormats()` 询问设备需要哪种，再决定加载 `.spv` 还是 `.dxil`。
- **易错点或关键取舍**：
  - **`shadercross` 不认 GLSL**（输入仅支持 SPIR-V / HLSL），所以必须"先 `glslc` 再 `shadercross`"，无法一步到位。
  - 需要 `glslc`（shaderc 端口）与 `shadercross`（sdl3-shadercross 端口）**两个**工具；二者已作为 **host 依赖**写入 `vcpkg.json`，随 `cmake --preset` 自动装入。缺工具时构建只警告不阻断，代价是**运行时才失败**。
  - 不要再写成"只编 SPIR-V"——这是已被实测推翻的旧结论（见 [devlog.md](devlog.md) 2026-09-25 第 4 条）。
- **相关**：ADR [0002-shader-dual-format-pipeline.md](adr/0002-shader-dual-format-pipeline.md)、`cmake/Shaders.cmake`、`engine/render/triangle_renderer.cpp`、`references/meshing-and-render.md` §6

### 世界定义 vs 世界状态

- **一句话定义**：**世界定义**是"这个世界本来长什么样"（种子、生成规则、可挖区域标记、配置表），**世界状态**是"玩家把它改成了什么样"（挖掉的土、堆起的堆、放置的物件、实体位置）。
- **在本项目里是什么 / 为什么需要**：这条区分决定**什么要落盘**。世界定义**不落盘**（可由种子 + 数据文件重建，只需记版本与哈希）；世界状态**必须落盘**，且只存脏数据（见 ADR 0006 与 `references/save-and-serialization.md`）。重建顺序固定为：**标记 → 生成初始密度/高度 → 叠加玩家改动**。
- **易错点或关键取舍**：**把可挖区域标记写进地形场或密度场**是典型错误——那会让"标记"变成世界状态，既污染生成结果又让存档无谓膨胀。标记是**输入**，不是结果。
- **相关**：ADR 0004、ADR 0006、`docs/tech-plan-v2.0.md` §2

### 固定步长累加器与动作状态输入

- **一句话定义**：固定步长累加器 = 把"帧间隔"攒起来、每满一个固定 `dt`（本项目 1/60 s）就推进一次逻辑，并限制单帧最多补 5 步；动作状态输入 = 把按键/鼠标原始事件在**每帧采样一次**后变成"动作"，上层只问"这个动作是否按住 / 是否本帧按下"。
- **在本项目里是什么 / 为什么需要**：两者共同保证**逻辑与帧率解耦**：前者让物理与角色手感不随帧率漂移（可变 `dt` 会改变跳跃高度与隧穿判定），后者保证同一帧内多个逻辑步**不会重复消费同一次点击**（否则点一下会挖两次）。
- **易错点或关键取舍**：① 插值系数（alpha）只用于渲染，**绝不能回写进逻辑状态**；② 单帧补步必须封顶，否则卡顿后会陷入"越补越慢"的死亡螺旋；③ 上层（`world/`、`game/`）**不得直接读 SDL 事件队列**。
- **相关**：`engine/core/fixed_step.hpp`、`engine/input/input_map.hpp`、`references/gameplay-v0.1.md`、ADR 0008

### Jolt `CharacterVirtual`：台阶上不去的真正原因

- **一句话定义**：`CharacterVirtual` 是 Jolt 提供的"角色控制器"——用形状扫掠 + 自带逻辑处理移动，而不是给胶囊挂刚体。
- **在本项目里是什么 / 为什么需要**：角色胶囊用手感优先的控制器（走 / 冲刺 / 跳 / 上坡 / 自动上台阶），地形碰撞用 `HeightFieldShape` 逐 tile 生成并在挖掘后重建。
- **易错点或关键取舍**：低速逼近台阶时中心过不去棱，**`mWalkStairsMinStepForward` 必须大于胶囊半径**（本项目取 `1.5 × 半径`）；`mWalkStairsStepUp` 需略大于台阶高（`+0.05` 余量）。另外 **vcpkg 的 `joltphysics` 5.6.0 未开 `JPH_DOUBLE_PRECISION`（`RVec3` = `Vec3`，单精度）**，与"世界定位用 `int`/`double`"的红线在大坐标上冲突 → 已登记为**待收敛项 7**。
- **相关**：`engine/physics/physics_world.*`、`world/terrain/terrain_collision.*`、`docs/plans/v0.1.md` T7

### vcpkg 的 ImGui 端口把后端编进了库本体

- **一句话定义**：vcpkg 的 `imgui` 端口会按所开特性**把后端源码一起编成 `imgui.lib`**。
- **在本项目里是什么 / 为什么需要**：开了 `sdl3-binding` + `sdlgpu3-binding` 后，`imgui_impl_sdl3.h` / `imgui_impl_sdlgpu3.h` 已随端口安装，**无需**再把后端 `.cpp` 加进自己的目标，只需 `find_package(imgui CONFIG REQUIRED)` + 链接 `imgui::imgui`。
- **易错点或关键取舍**：ImGui 需在每帧 `NewFrame` **之前**收到平台事件（`ImGui_ImplSDL3_ProcessEvent`）才能交互。本项目 `Window::pump_events` 独占事件队列且不外露，因此当前面板是**只读展示**（可用 F1 开关，不可拖动）——要交互须在平台层加事件外露钩子。
- **相关**：`game/debug_overlay.*`、`world/streaming` 无关；`docs/plans/v0.1.md` T9

### 输入边沿与固定步长的错配（会静默丢输入）

- **一句话定义**：如果"本帧按下"这类**边沿事件**在**帧边界**被消费清除，而真正用到它的是**固定步循环**，那么当某一帧的逻辑步数为 0（`plan.steps == 0`）时，这个边沿就被**无声丢弃**。
- **在本项目里是什么 / 为什么需要**：输入层每帧 `BeginFrame()` 采样一次（正确，避免同帧多步重复消费一次点击），但本机关闭垂直同步后渲染帧率可达 **~1400 FPS**，而逻辑固定 60 Hz ⇒ **约 96% 的帧没有逻辑步**。于是"按空格跳跃"这类边沿动作绝大多数被丢掉，表现为"按键没反应"。
- **易错点或关键取舍**：修法不是回到"每步都读原始输入"（那会重复消费），而是**帧级锁存**：帧边界只**记录**边沿，固定步循环消费并清除，保证"一次按下恰好生效一次"。任何新增的"按一下触发一次"的动作都要走这条锁存路径。
- **相关**：`engine/input/input_map.hpp`、`engine/core/fixed_step.hpp`、`game/main.cpp`、`docs/plans/v0.1.md` B3

### 退化视图矩阵：eye 与 target 重合或视线与上方向平行

- **一句话定义**：`lookAt(eye, target, up)` 需要 `eye≠target` 且视线方向不与 `up` 平行，否则构造基向量时归一化除零 ⇒ 得到 **NaN**，`viewProjection` 全 NaN ⇒ 顶点**全部被剔除**，画面只剩**清屏色**。
- **在本项目里是什么 / 为什么需要**：第三人称相机在"避障把跟随距离压到 0"并叠加"离地间隙"安全网后，会出现 `eye` 正上方等于 `target` 的退化情形——表现为**一堆土之后画面变成一片浅蓝**（清屏色 `(0.45,0.62,0.85)`）。
- **易错点或关键取舍**：相机避障/安全网这类"为了不穿模"的兜底逻辑，**必须同时保证几何不退化**（这里用 `kCameraMinDistance = 0.5` 托底最小跟随距离，且要在安全网**之前**生效）。凡是"把某个距离压到 0"的钳制，都要问一句：压到 0 之后矩阵还有意义吗？
- **相关**：`engine/render/camera.hpp`、`docs/plans/v0.1.md` B2

### 相对鼠标模式与"重捕获点击"的消费顺序

- **一句话定义**：`SDL_SetWindowRelativeMouseMode(win, true)` 会**隐藏光标**并把鼠标位移以**相对增量**持续送入事件队列——位移不再受屏幕边界限制。
- **在本项目里是什么 / 为什么需要**：第三人称 / 第一人称视角靠**累计相对位移**决定 yaw/pitch。非锁定模式下光标一撞屏幕边缘位移就停：按本项目灵敏度（`0.0022 弧度/像素`），从正前方转到单侧 ±89° 约需 **706 px** 累计位移，屏幕高度往往不够 ⇒ **俯仰根本推不到上限**，并且鼠标移出窗口后视角直接卡住。所以"锁定鼠标"与"能看满 ±89°"是**同一个问题的两个症状**。
- **易错点或关键取舍**：① **失焦必须自动释放**，否则 Alt+Tab 之后光标消失、无法操作其它窗口；② 重新捕获的**那一次点击必须先于笔刷判定被消费**，否则"点一下锁定鼠标"会顺带挖掉一格；③ 未捕获期间要**丢弃**位移，否则移动光标会带着视角转。这三点都写成了纯函数状态机并加了单测。
- **相关**：`engine/platform/window.hpp`、`game/mouse_capture.hpp`、`docs/plans/v0.1.md` T14、`docs/game-design.md` G8

### 菜单型 UI 打开时的输入抑制与鼠标捕获（业界标准做法）

- **一句话定义**：游戏里一旦有**可交互 UI**（设置 / 背包 / 菜单），标准做法是三件事一起做：① **释放鼠标捕获**（光标可见才能点）；
  ② **抑制游戏内输入**（视角、攻击、移动都不响应）；③ **关闭后恢复**打开前的捕获状态与输入。
- **在本项目里是什么 / 为什么需要**：本项目用 ImGui，抑制的判据是它的 `io.WantCaptureMouse` / `io.WantCaptureKeyboard`——
  **不要自己另发明一套"鼠标是否在面板上"的判断**；同时"面板打开"本身也应视为全量抑制（避免 ImGui 某一帧未报 Want 时漏抑制）。
  捕获恢复则必须**记忆打开前的状态**，否则"进游戏时已捕获"和"进游戏时未捕获"两种情形会走成同一种结果。
- **易错点或关键取舍**：① 相对鼠标（已捕获）期间要给 ImGui 置 `ImGuiConfigFlags_NoMouse`，否则无意义的绝对坐标会把 UI 误判为被悬停、反而抑制视角；
  ② 鼠标点击面板按钮**绝不能同时**挖/堆地形（否则"点一下设置"会改地形）；③ 是否暂停模拟要**显式决定并写明**——本项目选择**不暂停**（世界暂无自主运动实体，暂停会给固定步长引入第二个时间状态）。
- **相关**：`game/gameplay_input.hpp`、`game/system_panel.*`、`engine/platform/window.hpp`、`docs/ui-inventory.md` §2.1

### ImGui 默认字体不含 CJK 字形

- **一句话定义**：Dear ImGui 内置的默认字体只有 ASCII 字形，**直接写中文会显示为缺字方块**（不是乱码，是"豆腐块"）。
- **在本项目里是什么 / 为什么需要**：面板必须可读，故采用**三级字体解析**（仓库 `assets/fonts/` → 系统 CJK 字体（Windows `msyh.ttc` 等 / Linux Noto·文泉驿 / macOS PingFang）→ 无），
  并引出一条**"标签缝"**：所有标签一律经 `game/ui_text.hpp` 取词——**命中 CJK 字体用中文，否则整表纯英文**，因此**任何机器上都不会缺字**。
- **易错点或关键取舍**：① 字体文件较大（数 MB）且需指定 `GetGlyphRangesChineseSimplifiedCommon()`，占仓库体积与启动时间 ⇒ 本项目**默认不内嵌**，靠系统字体 + 英文回退；
  ② 回退必须**由代码保证**（遍历全部标签断言纯 ASCII + **扫描面板源码**禁止直接给 ImGui 传非 ASCII 字面量），否则新增标签时 `?` 又会冒出来；
  ③ 只有在"所有平台都统一中文"时才需要内嵌**子集化**字体（`Noto Sans SC`，OFL 1.1，约 1–3 MB）——**属新资产，须先登记**。
- **相关**：`game/system_panel.*`、`docs/ui-inventory.md` §2.1「可读性说明」

### 限帧：垂直同步 vs 睡眠限帧（禁止忙等）

- **一句话定义**：限制帧率的两条正规路径——**垂直同步**（呈现时阻塞等待显示器刷新，天然把帧率钉在刷新率、零忙等）与**限帧器**（睡到目标帧时间再继续）。
- **在本项目里是什么 / 为什么需要**：未限帧时若交换链用 Mailbox 呈现，帧率会飙到上千（本机 **360 Hz 显示器下实测 2000+ FPS**），纯属浪费 CPU / GPU 与功耗。规则：**目标 = 显示器刷新率 ⇒ 走垂直同步**；**目标 < 刷新率 ⇒ 关垂直同步 + 睡眠限帧**。
- **易错点或关键取舍**：① 限帧**必须睡眠**（一次 `SDL_DelayNS`），**不能用循环空转**——`SDL_DelayPrecise` 之类实现会忙等烧 CPU；② 睡眠只保证"至少睡够"，受 OS 调度粒度影响（Windows 约 1 ms），**实测 FPS 会略低于目标**，这是"零忙等"的正常代价；③ 上限值依赖**当前显示器**，所以设置里存**绝对值**、启动时按刷新率**重新钳制**（否则换显示器会留下不可能的值）；④ 刷新率查询取**窗口所在显示器**的桌面模式，别取错显示器。
- **相关**：`engine/core/frame_limiter.hpp`、`engine/platform/window.hpp`、`docs/ui-inventory.md`「帧数上限」

## E. 疑难问答

### Q1 为什么 D3D12 要 DXIL，而 Vulkan 要 SPIR-V？

两者是不同厂商体系的着色器中间表示：D3D12 只接受微软的 DXIL，Vulkan 只接受 Khronos 的 SPIR-V。SDL3_gpu 会按选中后端要求对应格式，喂错就直接断言失败。**本机没有可用 Vulkan，SDL 落在 D3D12，所以只产 SPIR-V 必然崩。**

### Q2 为什么方块碰撞不能用 Jolt / Bullet 这类通用物理引擎？

通用引擎为"任意凸体 + 大量动态物体"设计，走宽相 + 窄相 + 形状查询。而体素碰撞只需查玩家 AABB 周围的 3×3×3 个方块，是纯整数索引查询，能快上百倍。通用物理留给怪物、掉落物这类动态刚体。

### Q3 为什么只存"脏区块"？

世界由种子确定性生成，未修改的区块走到哪儿都能原样重建，只有玩家改过的必须落盘。这从根本上避免了"无限世界撑爆硬盘"。

### Q4 为什么世界坐标不能用 float？

float 只有 24 位有效位，离原点约 2²⁴ 格后精度不足 1 格，画面会抖。故世界坐标用整数，渲染时改用相机相对坐标。

### Q5 为什么贪婪合并的作用域只能到单个 Section？

顶点位置用 uint8 存相对坐标（0~16），表示不了跨 Section 的更大范围。

### Q6 `VCPKG_ROOT` 为什么会被"改掉"？

VS 的开发者环境脚本（`vcvars` / `Enter-VsDevShell`）会把它设成 VS 自带的 vcpkg。**必须在加载 VS 环境之后再设置 `VCPKG_ROOT`**，否则 Presets 指向错误的 vcpkg 实例，并连带产生 `Ninja not found` / `CMAKE_CXX_COMPILER not set` 之类的**级联误报**。

### Q7 CI 为什么会"0 job"？

GitHub 对**无效的 workflow 文件**（或 Actions 启动前置条件不满足）会创建一个结论为 `failure`、但**没有任何 job** 的运行，且 `created_at` / `updated_at` / `run_started_at` 三个时间戳完全相同。这表明失败发生在**启动阶段**，不是构建失败。

### Q8 `.ps1` 为什么必须写成纯 ASCII？

Windows PowerShell 5.1 读取无 BOM 的 UTF-8 文件时会按本地代码页（中文环境为 GBK）解码，某些中文字节会解出 `\`，把字符串的收尾引号转义掉，导致整个文件语法崩溃。CI 脚本用纯 ASCII 即可规避。**注意：这是编码问题，不是行尾问题——LF 行尾的 `.ps1` 在 PowerShell 5.1 下完全正常。**

### Q9 装了 clang 为什么还不能编译？

Windows 上 clang 只是编译器前端，仍需要 Windows SDK 的头文件 / 库与 MSVC STL。所以 VS Build Tools 不可跳过；clang 当前的价值在 clang-format / clang-tidy。

### Q10 winget 的 portable 安装为什么失败？

winget 会在 `%LOCALAPPDATA%\Microsoft\WinGet\Links` 下创建符号链接，该目录缺失时报 `create_symlink: The system cannot find the file specified`。补建该目录即可，或直接手动解压到自定义目录（本项目 Ninja / sccache 就是这么装的）。

### Q11 为什么规范里要强调"正向写法优先"，而不是直接列禁止项？

处理"禁止 X"时需要先表征 X 再取反，长上下文里这一步容易丢失；同时解释性文字会把 X 这个名词注入上下文，反而提高它被采用的可能。所以规则尽量写成"必须执行 Y"，把禁令集中到**可机械执行的门禁脚本**里。

### Q12 "常驻文档"为什么值得单独立规矩？

因为知识有三种不同的去处，混在一起会同时变差：**概念**（是什么）→ 学习笔记；**过程**（做了什么、为什么、验证）→ 开发记录；**决策**（选了什么、备选、切换条件）→ 方案文档 / ADR。分开写之后，三者各自可检索、可维护，也不会互相覆盖。

### Q13 地表材质该用贴图吗？"直接渲染开销太大所以要贴图"这个判断对吗？

**结论：该用贴图，但理由是"外观"，不是"性能"；这个判断方向反了。**

- **贴图买到的是细节密度**：3A 观感靠的是"每像素的表面细节"（颗粒、裂纹、法线起伏），这些用几何或顶点色做不出来——本项目此前是 4 个占位纯色 + 逐顶点权重，所以棱角处只能糊成一条宽带。
- **贴图不是免费的**：真正的开销是**采样带宽**（每层 albedo + 法线两次带过滤的采样），逐像素算权重反而很便宜。所以"直接渲染开销太大 ⇒ 改用贴图"不成立；正确表述是"想要细节 ⇒ 必须用贴图 ⇒ 再用层数裁剪控制带宽"。
- 本项目落地：**逐像素权重 + 分层 albedo/法线贴图 + 只采权重最高的 3~4 层**，见 [ADR 0009](adr/0009-terrain-material-pipeline.md)。

### Q14 想提升画面观感，为什么**必须先做 HDR 与色调映射**，而不是先做阴影或 PBR？

因为**顺序错了会把收益吃掉**。

- 没有色调映射时，颜色超过 1.0 就被**硬截断**成纯白。阴影的价值在"亮部与暗部的层次"、PBR 的价值在"高光的形状"——这两样恰恰都发生在**亮部**，会最先被截断抹平。所以先把 HDR + 色调映射做掉，它们才有地方表现。
- 反过来，色调映射本身就能显著改善"发灰、没动态范围"，是**单步回报最高**的一步。
- 本项目据此把顺序**固定为四步且不得跳步**（[ADR 0010](adr/0010-render-quality-pipeline.md)）：① HDR + 色调映射 → ② 阴影 + 天空光 + 雾 → ③ PBR + roughness/AO → ④ MSAA + 细节法线。

### Q15 SDL3_gpu 能测每帧 GPU 耗时吗？

**不能。** SDL3_gpu 没有时间戳 / 查询对象的 API，无法得到"阴影通道耗时 1.2 ms"这类数据。

- 因此本项目 F1 面板对该项**显式显示"不可用（SDL3_gpu 无时间戳查询）"**，而不是编一个数字（SKILL 第七节：不得用假数据充数）。
- 能拿到的是**引擎侧记账**：Draw Call 数、三角形 / 顶点数、纹理显存、CPU 三段耗时（逻辑 / UI / 提交）。这些足以判断"改动的代价是否可接受"。
- 真要 GPU 级剖析，得绕过 SDL3_gpu 直接用后端原生 API（Vulkan timestamp query / D3D12 query heap），属**另开 ADR 的选型变更**，当前不做。

### Q16 一个着色器阶段能同时绑几组 uniform？

SDL_gpu 的**每个着色器阶段有 4 个 uniform 槽**（`SDL_gpu.h` §Uniform Data），用 `SDL_PushGPUFragmentUniformData(commandBuffer, slot, ...)` 按槽上传，GLSL 侧对应 `layout(set = 3, binding = N, std140)`。

- 本项目片元的用法：**槽 0 = 材质参数**（`MaterialUniform`，ADR 0009 的单入口投影）、**槽 1 = 光照与雾**（`LightingUniform`）。两者都在**管线创建时**声明 `num_uniform_buffers = 2`（少声明会断言）。
- 易错点：① 槽号必须与 `binding` 号一致；② 每个槽的内容要**保持不变式**——同一槽的所有推送必须来自同一份配置表，否则又变成"两处事实来源"；③ 推送发生在**开启渲染通道之前**（`SDL_PushGPU*UniformData` 是命令缓冲级调用，不是渲染通道级）。

### Q17 SDL3_gpu 能用"只有顶点着色器"的管线吗（例如只写深度的阴影通道）？

**不能。** 实测 `SDL_CreateGPUGraphicsPipeline` 会断言 `!"Fragment shader cannot be NULL!"`（本仓库在 T21b 首次冒烟即命中）。

- **正确做法**：深度通道**照样挂一个片元着色器**，但让它成为**空入口**——`num_color_targets = 0`，着色器不做任何计算、不写任何输出；深度写入由**光栅化阶段**完成（`depth_stencil_state` 已开深度测试与写入）。
- 本仓库落地：`assets/shaders/shadow.vert` + `shadow.frag`（空片元入口），见 `references/meshing-and-render.md` §4 的硬规则。
- 顺带一条：阴影图的采样器要用 **`NEAREST`** 而不是线性过滤——线性会在两个表面之间插出非物理深度、让 PCF 比较失真；PCF 的平滑靠**手动 3×3 邻域**获得。
