# 游戏设计（本项目要做的游戏）

> **性质**：本仓库的**内容基线文档**之一（见 `.trae/skills/voxel-engine-dev-standards/SKILL.md` 第六节）。
> **层面**：**游戏层** —— 这里写"**我们要做哪款游戏、要求什么**"，与"引擎能做什么"分开。
> 引擎的通用能力见 [引擎能力与产出范围](engine-capabilities.md)；世界背景见 [世界观设定](world-setting.md)；
> NPC 见 [NPC 行为逻辑](npc-behavior.md)。
> **维护义务**：任何一次改动**新增、修改或移除游戏需求 / 玩法规则 / 阶段范围**，必须**同一次提交内**更新本文件。
> 未实现的需求**先占位**（状态 `未开始`），不得留白。

## 1. 这是一款什么游戏

**修仙题材的开放大世界游戏**（当前阶段的全部需求见 §2）。

| 项 | 结论 | 依据 |
| --- | --- | --- |
| 题材 | **修仙大世界** | 项目所有者确认（2026-09-25） |
| 视角 / 控制 | 第三人称，玩家控制自己的角色 | 同上；引擎侧已有第三人称相机与胶囊角色 |
| **产物定位** | **这是一款游戏引擎**；**引擎层与游戏层分开**，且**先为当前这款游戏做引擎** | 项目所有者确认（2026-09-29）；执行口径见 `.trae/skills/.../SKILL.md`「产品方向与防走偏标尺」 |
| **玩法形态** | **PvE + PvP**，在**随机生成或固定生成的地图**里**战斗** | 项目所有者确认（2026-09-29）；阶段位置见 §2.4 |

| 商业模式 / 平台 | 待补 | 待项目所有者提供 |

**通用约定**

- **能力清单里的每一条都必须可判定**（有参数或可观察现象），不得只写"支持 X"。
- **主角与 NPC 的能力差异**（数值、感知、权限）在 NPC 阶段写明；底层能力不各写一套。
- **连带必做项（2026-09-27 起）**：按 SKILL「世界内一致性」节，**"用户明确提出的破坏 / 交互"所必然带来的连带后果，属于该需求的一部分**
  （例：挖了洞 ⇒ 洞要能进去；承重被毁 ⇒ 上部要塌）。本表里带 **"连带必做项"** 字样的行就是由该审查识别出来、
  但**尚未实现**的项；**它们的降级或分期交付必须先经项目所有者确认**，不得默默计入"遗留"。
- **已登记的降级（2026-09-29，性能；所有者裁定"改默认值"）**：**光球爆炸的腔体大小**由 `projectiles.toml` 的
  `explosion_radius` 决定，因"挖洞当帧成本"实测过高而 **6.0 → 4.0 格**。
  - ① **降到什么程度（可判定的差异）**：草地里的**腔体半径被钳到 4 格**（体积 ≈ 原来的 1/3）；**区域外地表爆破坑**同步 6 → 4 格

    （只是"伤害预算不再是用尽的约束"这一件事变了）。

1. **先登记后动手**：任何新玩法需求先在 §2 补一行（状态 `未开始`），再实现，完成后回填。

3. **不写"A 或 B"**：涉及技术选型的（如物品系统怎么存、飞行的实现方式），候选与理由写 **ADR**。

5. **需求与引擎能力联动**：需求若依赖引擎缺失的能力，必须同时在 `engine-capabilities.md` 占一行，
