/ [ADR 0019](adr/0019-ambiguous-cell-vertex-splitting.md)**：歧义 cell / 歧义面按实体侧连通分量拆顶点 ⇒ **不再出现"某个面透明 / 缺面"**）；落定回写仍有 ≤1 格的落格离散化残余（机制性）。**真实感（T43 / [ADR 材质的分量**不删**，守卫已接、完整"不可破坏"语义待 T31）。**落地后的表示按材质分流（T46 / [ADR 0017](adr/0017-landing-by-material-rigid-vs-granular.md)；T50 起判据 = **碎块子块自己的材质**）**：**岩石等刚性碎块落地后形状完全不变**（保留自身几何体、不回写成地形；**光球打到它时在它的自身体素补丁上就地雕刻** ⇒ 只少被炸掉的部分、形状依旧、也不会被光球穿过）；**泥土等散体碎块落地后与地面融为一体**（体素化回写）且**接地沉降**（T51 起：降不到支撑的残留**直接清除**并打 WARN ⇒ **绝不会看到悬空的泥土**）。材质的这一区别由 `materials.toml` 的 **`rigid_debris`** 配置（岩 = true，草 / 土 / 沙 = false）驱动。**求解 scope 与表示守恒（T49 / T50 / [ADR 0018](adr/0018-structural-support-and-representation-preserving-destruction.md)）**：① **支撑求解的 **通用约定**

- **能力清单里的每一条都必须可判定**（有参数或可观察现象），不得只写"支持 X"。
- **主角与 NPC 的能力差异**（数值、感知、权限）在 NPC 阶段写明；底层能力不各写一套。
- **连带必做项（2026-09-27 起）**：按 SKILL「世界内一致性」节，**"用户明确提出的破坏 / 交互"所必然带来的连带后果，属于该需求的一部分**
  （例：挖了洞 ⇒ 洞要能进去；承重被毁 ⇒ 上部要塌）。本表里带 **"连带必做项"** 字样的行就是由该审查识别出来、
  但**尚未实现**的项；**它们的降级或分期交付必须先经项目所有者确认**，不得默默计入"遗留"。
- **已登记的降级（2026-09-29，性能；所有者裁定"改默认值"）**：**光球爆炸的腔体大小**由 `projectiles.toml` 的
  `explosion_radius` 决定，因"挖洞当帧成本"实测过高而 **6.0 → 4.0 格**。
  - ① **降到什么程度（可判定的差异）**：草地里的**腔体半径被钳到 4 格**（体积 ≈ 原来的 1/3）；**区域外地表爆破坑**同步 6 → 4 格
    （`explosion_depth` / `explosion_rim` 不变）。**伤害数值 `damage = 10` 未改** ⇒ 对**固定器物 / 后续战斗**的伤害语义不变
    （只是"伤害预算不再是用尽的约束"这一件事变了）。
  - ② **为什么（具体约束 + 依据）**：debug 实测**单发当帧 = 挖除 + 倒塌 ≈ 50 ms**（挖除 avg/max **33.10 / 43.47 ms**、
    倒塌 **16.94 / 39.63 ms**），是一帧预算（16.7 ms）的 **3 倍** ⇒ 每次开炮必然产生一次帧尖峰；而 `CarveByDamage`
    的**候选格数按半径三次方增长**，6 → 4 使挖除降到 **13.45 ms / 峰值 17.47 ms（−59%）**。
    三档对照（基线 / 关塌落 / 减小体积）与全部实测数字见 `docs/devlog.md` 2026-09-29 的 T71 条目（原始日志 `build/perf/*.log`）。
  - ③ **备注（何时补上、切换条件）**：满足任一即调回（先试 **5.0**，按实测模型 ≈ 21 ms/发，或直接回 6.0）——
    **(a)** release 复测显示"挖除"已远低于帧预算；**(b)** `CarveByDamage` 的候选枚举 / 材质查询被优化或**下沉到工作线程**；
    **(c)** 玩法上需要更大的破坏腔体（例如战斗设计明确要求"一炮轰开建筑"）。

## 5. 登记规则

1. **先登记后动手**：任何新玩法需求先在 §2 补一行（状态 `未开始`），再实现，完成后回填。
2. **可判定**：每行的"实现方式 / 落点"必须具体到模块或文件；写"用某个系统实现"这类空话视为未填。
3. **不写"A 或 B"**：涉及技术选型的（如物品系统怎么存、飞行的实现方式），候选与理由写 **ADR**。
4. **不虚构设定**：主角身份、境界体系、门派、地名一律来自项目所有者，未提供就标 `待补`。
5. **需求与引擎能力联动**：需求若依赖引擎缺失的能力，必须同时在 `engine-capabilities.md` 占一行，
   并在阶段计划里给出实现任务。
