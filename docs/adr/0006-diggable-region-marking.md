# ADR 0006：可挖区域标记 = 程序化规则 + 数据文件叠加

- **状态**：已采纳
- **日期**：2026-09-25
- **相关**：ADR 0004（硬约束 2：可挖范围由**显式标记区域**决定）；ADR 0005（TOML 解析）；`SKILL.md` 待收敛项 2；`docs/plans/v0.1.md` P2
- **收敛**：`SKILL.md` 待收敛项 **2**（可挖标记规则与文件格式）——本 ADR 落地后该项关闭

## 背景

ADR 0004 定下两条与"可挖范围"有关的硬约束：**可挖区域由显式标记决定**（区域外不可三维挖掘）、
以及**洞穴体积按固定网格对齐**。但当时没有回答：**这些标记从哪来**。已登记为待收敛项 2。

需求侧的原话是"地下部分要求在一定空间内能自由挖掘""要洞穴，但不必任意掏""由标记区域决定"。
这同时排除了两个极端：

- **纯程序化**：自然洞穴可以生成，但**无法手工放置一条废弃矿道**或某个特定洞窟；
- **纯数据文件**：世界一大、标记量就爆炸，且失去"按噪声自动长出洞穴系统"的能力。

另外必须满足既有红线：**生成逻辑必须是"只看当前区域 + 种子即可重建"的纯确定性函数**
（不得依赖 `rand()`、时间、线程顺序），否则未修改的区域无法靠种子重建、也不需要存盘这一前提就不成立。

## 决策

**标记由两个来源叠加，顺序固定：先程序化规则，后数据文件覆盖。**

### ① 程序化规则（纯函数）

- 输入：`(全局种子, 区域坐标)`，输出：该区域的可挖模式。
- 判据（纯整数/浮点确定性函数，不依赖全局状态、不依赖遍历顺序）：
  - **深度带**：地表以下 `min_depth` 才开始出现可挖体积；
  - **噪声阈值**：3D 噪声（FastNoiseLite，与地形同一套种子派生）超过阈值处为"洞穴可挖"；
  - **连通性约束**：只在噪声连通区域内成洞，避免生成孤立的小空腔（降低无谓的体积块数量）。
- 规则结果**不落盘**，永远可由种子重建。

### ② 数据文件（显式叠加）

- 位置：`assets/config/dig_regions.toml`（TOML，见 ADR 0005），随世界定义一起版本化。
- 字段规格（**冻结；变更须提版本**）：

  ```toml
  schema_version = 1

  # mode: "diggable" = 区域内可三维挖掘
  #       "sealed"   = 区域内强制不可挖（覆盖程序化规则）
  # priority 大者覆盖小者；同优先级时文件覆盖规则
  [[region]]
  name       = "abandoned_mine_01"
  mode       = "diggable"
  priority   = 10
  min        = [-64, -40, 128]     # int32 × 3，闭区间（方块坐标）
  max        = [ 64, -8, 256]
  ```

- **合并顺序**：`程序化规则` 先算 → 数据文件按 `priority` 升序覆盖 → 得到最终标记。
- 数据文件缺失时：只用程序化规则（**不报错**，便于空项目起步）；文件存在但校验失败：**报错中止启动**。

### ③ 运行期形态与缓存

- 标记按**固定网格的对齐单元**（与可挖体积块同格，见 ADR 0007/0008）缓存为紧凑位图或区间表，
  由流式加载器按需查询；缓存可丢弃、可重建。
- **不允许**把标记写进地形场或体积密度场 —— 它是**世界定义的输入**，不是世界状态。

### 与存档的关系

- 标记 = **世界定义**：随存档记录 `dig_regions` 的 `schema_version` 与内容哈希；不匹配时提示而**不是静默迁移**。
- 玩家的挖掘结果 = **世界状态**：作为"脏体积"落盘（沿用"只存脏数据"策略）。
- 因此重建顺序固定为：**标记 → 生成初始密度 → 叠加玩家改动**。

## 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **规则 + 文件叠加**（采纳） | 自然洞穴自动生成，人工洞窟/矿道可手工指定；两者都是确定性的 | 需要维护合并优先级语义与版本号 | **采纳** |
| 纯程序化规则 | 无需人工维护数据，世界完全由种子决定 | 无法手工放置特定洞窟/矿道；后期做关卡内容受限 | 不采纳（丢失内容控制力） |
| 纯数据文件 | 完全可控、所见即所得 | 大世界标记量爆炸；丧失自动洞穴系统 | 不采纳 |
| 由场景编辑器标注 | 最直观 | **场景编辑器是 POST-V0.5 暂缓项**，现在启动即违反范围控制 | 不采纳（后期可把编辑器输出写成同一份 TOML） |

## 后果

### 正面

- "一定空间内自由挖掘"有了明确、可测、可版本的边界；区域外一律不可挖，性能与玩法都受控。
- 规则部分不落盘，符合"未修改区域靠种子重建"的既有前提。
- 后期做编辑器时，**输出格式就是这个 TOML**，不需要改世界层。

### 负面 / 必须承受的代价

- 多一份需要人工维护、需要版本号的资源文件。
- 合并语义（优先级、覆盖规则）必须写进测试，否则"为什么这里能挖"会变成不可复现的问题。
- 程序化规则的阈值调参影响体积块数量，进而影响内存与网格化开销（预算见 ADR 0008）。

## 何时需要重新审视

1. 需要**运行时动态生成**可挖区域（例如任务系统开凿新矿道）→ 需扩展为"世界状态"并落盘，届时须重审本 ADR。
2. 可挖区域规模显著扩大（接近"整个地下层"）→ 回到 ADR 0004 的重审条件 2，评估 SVDAG 等方案。
3. 若后期引入场景编辑器并直接输出本格式，需补一条"编辑器输出 → 同一 TOML"的兼容性说明。
