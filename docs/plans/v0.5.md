### 1.5 **V0c 施工细则（物件生命周期：失支撑掉落 + 可破坏）**（2026-10-06）

- **来源（缺陷 + 所有者裁定）**：人工实测报告"在地上挖坑后物件**不掉落、不破坏**"。真伪判定：
  ① **不掉落 = 确认是缺陷**（违「世界内一致性」：承重/地基被破坏 ⇒ 上部不得**悬空不动**）；
  ② **不破坏 = 已登记**（V6）。所有者裁定：**掉落按 A（失支撑 ⇒ 转动态刚体）**；
  **破坏按 C（按类型分流）**，并**做成配置项**，**分别创建实例**供人工测试。
- **范围**：① **失支撑 ⇒ 静态体转动态刚体**（掉落；复用既有 Jolt 动态凸包路径，非新物理系统）；
  ② **爆炸命中** ⇒ `destructible_enabled && type.destructible` ⇒ **摧毁消失**；否则 ⇒ **只被炸飞 / 掉落，不破坏**；
  ③ **配置项**：`objects.toml` 增 `destructible_enabled`（全局开关，缺省 `true`；按 SKILL「已实现能力只允许配置项关闭」）；
  ④ **测试实例**：放置清单增一对"可破坏 / 不可破坏"对照实例。
  **明确不做（本步）**：物件**破坏状态持久化**（存档未开始）、**凹形物件的多凸包**（`ConvexHullDesc` 会填平凹形，当前三形态皆凸）、
  物件的**联网同步**、按伤害预算的**多段血条**（当前 `prop_damage_threshold = 0` ⇒ 单发命中即破，与破坏表一致）。
- **顺序**：0.1 配置项（`ObjectTable.destructibleEnabled` + `objects.toml` + 测试实例）→ 0.2 支撑探测纯函数（`object_support.hpp`）→
  0.3 `game/main.cpp` 接线（支撑检查 → 转动态 → 每帧同步位姿；爆炸 → 摧毁 / 炸飞）→ 0.4 单测 → 0.5 文档同步。
- **落点**：`world/object/object_layer.{hpp,cpp}`、**新增** `world/object/object_support.hpp`、`assets/config/objects.toml`、
  `game/main.cpp`、`tests/object_layer_test.cpp`、**新增** `tests/object_support_test.cpp`、`tests/CMakeLists.txt`、
  `docs/engine-capabilities.md`、`docs/file-index.md`、`docs/game-design.md`、`docs/devlog.md`。
- **验收判据（可判定）**：① 炸掉物件**脚下**的地面 ⇒ 物件**掉下去**并停在新地面（不再悬空）；
  ② `destructible_enabled = true` 时爆炸命中土堆 / 木箱 ⇒ **消失**（网格 + 碰撞体一并移除），石块**不消失**（只被炸飞）；
  ③ `destructible_enabled = false` 时 ⇒ **任何物件都不消失**（只被炸飞）；
  ④ 配置非法（`destructible_enabled` 非布尔）⇒ **启动失败**；⑤ 构建零警告 + `ctest` 全绿 + 门禁 0 违规。
- **3A 基线三问**：
  1. **业界参照**：**7 Days to Die**（结构完整性 SI：失支撑方块塌落）、**Space Engineers**（失支撑网格转**动态刚体**）、
     **Teardown / Fortnite**（失支撑即倒塌）、**Minecraft 重力方块**（最简：失支撑即下落）；破坏分流参照 **R6S / BF 的局部破坏**。
  2. **本项目 3A 基线形态（可判定）**：失支撑 = **确定性判据**（底面若干探测点全为空 ⇒ 无支撑）⇒ 转 `AddDynamicConvexHull`
     （与 ADR 0015/0017 的"失支撑 ⇒ 动态刚体"**同一口径**，不引入第二套物理）；破坏 = **按类型 + 全局开关**、
     **数据驱动**（`destructible` / `destructible_enabled`），不是硬编码。
  3. **是否降级**：**有**（所有者已确认）——① 不作**破坏状态持久化**（存档未开始）；② 无**凹形多凸包**；
     ③ 无**多段血条**（单发即破）；④ 支撑检查为**固定探测点 + 固定间隔**（非连续接触求解）。
     **切换条件**：存档启动 ⇒ 持久化；出现凹形物件 ⇒ 多凸包；需要"打几下才破" ⇒ 接伤害预算。
- **世界内一致性**：**真实世界** —— 地基被挖 ⇒ 物件**必须落下**（不得悬空）；被炸 ⇒ 可破坏者**消失**、不可破坏者**被炸飞**。
  **修仙世界** —— 仍为**临时占位内容**，**不引入新设定**（"此物为何可破坏 / 被毁后如何"待所有者提供，见 `world-setting.md` §3）。

- **尺寸发现（先报告，再改计划）**：`game/main.cpp` **3701 行**，其中**世界级局部状态 40+ 个**

- **C 碰撞体（`game/main.cpp`）**：**偏离了本节原列的两种做法，改用"消除无谓重建"**（见下方偏离说明）：
  relod / 重传只改**网格 LOD、高度不变** ⇒ Jolt 高度场内容不变，而 `TerrainCollision::SyncTile` 对已有体会
  **无条件 `UpdateHeightField`**（单次 4–6 ms）。新增 `reconcileTerrainCollision()`：只做**存在性对账**
  （`距离内 && 非空网格` 与 `collisionActive` 一致即**一个字节都不动**），两条 relod 路径改用它。
  真正的重建只可能来自**高度变化**（笔刷 / 爆破），那些路径本就显式 `SyncTiles`，不受影响。
- **新增观测设施（永久）**：尖峰日志增加「**流式积压**」一行 —— `待建 / 待卸 / 待LOD / 暂存 / 在飞 + 本帧是否追平`。
  这正是本次定位到"每帧只装 1 个"的证据；预算类改动必须有它，否则"追不上"只会表现为尖峰变多而看不出原因。
- **实测（A 世界 10 km，`--world=world_a --auto-test --autofly=60`；飞行 60 s 全程覆盖，`同步回退 0 次`）**：
  | 指标 | 基线（P5 后，p6a） | **A+B+C（本次）** |
  | --- | --- | --- |
  | 安装段峰值 | ≤ 19.28 ms | **≤ 4.1 ms** |
  | 碰撞重扫段峰值 | ≤ 7.27 ms | **≤ 4.2 ms** |
  | 碰撞体同步峰值 / >5 ms 次数 | ≤ 14.4 ms / 16 次 | **≤ 4.5 ms / 0 次** |
  | 更新收包段峰值 | ≤ 15.52 ms | ≤ 13.1 ms |
  | 整帧 > 50 ms 的帧 | 2 帧 / 23 s 飞行 | **1 帧 / 60 s 飞行** |
  | 飞行中"窗口调整完毕" | 约每 1–2 s 一次 | 29 次 / 60 s（**追得平**） |
- **未达标（如实登记）**：验收判据 ②「`地表常驻` ≤ 4 ms」**未达成**（实测最坏 44.9 ms）。两个残余**不是**
  A/B/C 能解决的：
  1. **`更新收包` ≤ 13.1 ms 未纳入预算** —— 主体是 `TerrainTileScheduler::Update` 的**整窗重规划**（原子、不可分帧）。
     下一步应做"增量规划"（只算进出窗口的那一圈），**属新条目，未开工**。
  2. **单件不可分割的 GPU 上传停顿**（实测单次 relod 上传 **33.4 ms**，同期碰撞体同步 0.00）——
     SDL_gpu 的缓冲创建 / 上传偶发停顿，**任何毫秒预算都挡不住**；且伴随 env 噪声（既有的 1410 ms 帧同类）。
- **偏离说明（C 的做法）**：本节原列两条路线，实做时**两条都不可用/不划算**，故按"更小改动、更确定收益"另择：
  ①「下沉 worker」需新增物理层"预备形状 + 主线程装配"API（Jolt 形状创建线程安全、**装配不是**），
  属架构改动 + 需 ADR + 所有者签字；②「批量后统一 `OptimizeBroadPhase`」与 `physics_world.hpp` 既有注释
  （"**不需要**在批量增删静态体之后反复调用"）冲突，且实测成本在**形状构建**而非宽相位 ⇒ 预期**加成本**。
  ③故改为**消除无谓重建**（本次实测碰撞体同步 >5 ms 次数 16 → **0**）。若所有者仍要"① 下沉 worker"
  （可进一步消掉**半径边界真实建体**那部分 ≈2–4 ms/次），需先裁决线程契约，再开新条目。

#### 1.17.2 P6 收尾（2026-10-06，所有者指示"做建议 2、3、4"）

- **② 流式回归护栏（已落地）**：新增 `tools/vx_stream_regression.ps1`（纯 ASCII；ASCII 标记驱动，不依赖中文字面）。
  **断言**：① 飞行中"常驻集合已随窗口调整完毕"（`ADR 0024` + `worker` 双标记）≥ `-MinSettle`（缺省 5）；
  ② 每次 settle 的**同步回退 = 0**；③ 积压样本（`P6-A`）的 `unload` 峰值 ≤ `-MaxUnloadBacklog`（缺省 400）；
  ④ 帧尖峰 count / max / >50 ms 只**上报不判定**（本机有环境噪声）。自关闭（`CloseMainWindow`，不 kill）。
  **为什么必须有**：P6-A 那次"每帧只装 1 个"的缺陷**在帧时间里看不出来**（只表现为"尖峰变多"），
  只能靠人读日志发现；脚本把它变成**失败退出码**。**已自证**：先跑出一次 `FAIL`（脚本自身的解析 bug ——
  把启动期的 `地表 tile 常驻集合（ADR 0024）` 行误当 settle 行），修好后 `PASS`。
- **③ 「更新收包」再拆一层 → 结论：增量规划【不做】（数据否决）**：给 `更新收包` 加了
  `计划（Update）/ 收包 / 预取` 三个子计时。**三次同条件长跑的实测**：

  | 子项 | 均值 | 峰值（三次） |
  | --- | --- | --- |
  | **计划 = `TerrainTileScheduler::Update`（整窗重规划）** | **1.05 – 1.32 ms** | 4.69 / 4.73 / 4.73 ms |
  | 收包（worker 结果安装） | 3.4 – 3.8 ms | 11.93 / 12.24 ms |
  | 预取（提交 worker 任务） | 1.14 – 2.39 ms | **47.83 / 9.31 ms** |

  ⇒ **`Update` 只有 ~1 ms 量级，根本不是瓶颈**（原先 §1.17.1 把 `更新收包` ≤13.1 ms 归因于它，
  是**没拆开看**的误判）；预取/收包的峰值在两次同条件长跑里相差 **5 倍**（47.8 → 9.3），
  说明**由调度/抢占噪声主导，不是稳定的算法成本**。故"增量规划"**判为不做**（收益 <1 ms，代价是一次
  确定性敏感的整窗重写，性价比不成立）。这正是"先定位再改"的应有结果。
- **③ 顺带的三处低成本改动（如实登记：未测出收益）**：`Update` 只物化一次 `ResidentTiles()`（原先两次）、
  `PlanFromDesired` 的 `is_sorted` 快路径（省一次整窗拷贝 + 排序）、`desired.reserve(window.TileCount())`；
  `TerrainTileBuildPipeline` 的完成队列改 `std::deque`（`pop_front` O(1)，原 `erase(begin())` 要搬移整队、
  元素含 8 KB `TerrainTile`）+ 在"本轮收包弹空"时**只回收一次**在飞任务（原为每弹一个就 O(在飞) 重扫）。
  **理由**：复杂度严格更优、语义逐位不变、并消掉一条**写错的假设**（原注释"队列长度 ≤ 数十量级 ⇒ 搬移可忽略"，
  而队列上限 = 预取提前量 192）。**实测未变**（drain 均值 3.4 → 3.8、峰值 11.9 → 12.2）⇒ 如实记录为"潜在修复"。
- **③ 新登记项（方向待所有者定）**：真正的残余是 **worker 侧单 tile 计算峰值 ≈110 ms（debug）**，与飞行期
  瓦片需求（跨 tile 约 67 建 + 约 50 relod / 0.7–1.5 s）**同一量级** ⇒ 主线程在 `Submit` / 收包上受**背压与
  抢占**，表现为 `更新收包` 偶发 10–50 ms。三条候选（**①涉及降级，须先问**）：
  **(1) 缩常驻窗口**（4489 → 更小；直接降量，但属**画质 / 可见距离降级**，须所有者裁决）；
  **(2) 优化 worker 侧构建**（噪声评估 / 网格化；不改可见结果，但改动面在生成与网格化）；
  **(3) 先按 release 复测**（debug 的 `_ITERATOR_DEBUG_LEVEL=2` + 无优化会放大数十倍，很可能 110 ms → 数 ms）。
- **④ V7 验收判据【已重校准为"密度阈值型"】**（所有者 2026-10-06 裁定 → 口径见
  [SKILL 第四节](../.trae/skills/voxel-engine-dev-standards/SKILL.md) + 数量唯一来源
  [`references/performance-and-hitches.md`](../.trae/skills/voxel-engine-dev-standards/references/performance-and-hitches.md) 的「总判据」）：
  稳态 **P99 ≤ 2× 帧预算（33 ms）** + **> 50 ms 帧 ≤ 6 帧 / 60 s**（且每帧须**可解释**）+ **最坏单帧 ≤ 80 ms**。

  ③ 输出坐标全部落在 `[0,1]²`、`shade ∈ [0,1]`；④ **深度升序**（远先画）；⑤ **同输入同输出**（确定性）；

  （前置 = 渲染器"渲到任意纹理"公开 API + LDR 小管线 / 目标 + ImGui 纹理接线），见 ADR 0032 备选表 / §四第 5 条。
