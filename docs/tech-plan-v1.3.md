# 超大世界体素游戏引擎开发技术栈方案

> 目标：使用 **C++ 从零开发一款自研游戏引擎**，并基于该引擎开发一款**超大世界、程序化随机生成的三维体素游戏**（类《我的世界》）。
>
> 本文档整合了引擎底层通用技术栈与体素超大世界专属模块，给出完整的技术选型（含选型理由、备选项对比、优劣性分析与切换条件）、架构设计、第三方库清单、性能红线与分阶段落地路线，作为项目的总体技术纲领。
>
> **阅读约定**：文中「采用 / 首选 / 结论」为**实际技术决策**；「备选方案」为**默认不启用**的兜底项，仅在出现明确切换条件并经确认后启用，不是并行候选。标注「暂缓（POST-V0.5）」的条目属于**范围控制**（不主动实现），不是待办。

## 1. 项目目标与范围界定

### 1.1 核心目标

| 目标 | 说明 |
| --- | --- |
| 自研引擎 | 使用 C++ 从零构建一套可复用的游戏引擎，具备渲染、输入、资源、物理、脚本等通用能力 |
| 超大世界 | 支持近乎无限的程序化生成世界，通过流式加载实现"走到哪生成到哪" |
| 随机生成 | 每次开新档依据随机种子与生成逻辑，产生符合逻辑（地形、洞穴、生物群系、结构）的新世界 |
| 自研游戏 | 用该引擎开发一款可玩的三维体素游戏（建造、破坏、生存探索） |

### 1.2 关键差异：为什么不用 Unity / Unreal

- 通用引擎需要适配所有类型的游戏，存在大量与体素场景无关的冗余开销；对于"以区块为单位重建网格"这种核心循环，通用引擎的组件/GameObject 模型反而成为性能天花板。
- 自研引擎可针对体素场景做**极致定制优化**（区块化内存布局、贪婪网格化、体素光照、专用碰撞），理论性能上限更高。
- 代价是开发周期长、工作量大，必须**严格控制范围、分阶段迭代**，不要一开始就追求大而全。

> **选型对比**：是否直接用现成引擎？
> - **候选 A：Unity**。优点：上手快、生态大、体素插件（如 Voxel Play、MagicaVoxel 工具链）齐全。缺点：C# GC 停顿、C++ Job System 之外的 Mesh 重建吞吐有限，超大视距下 Draw Call 与 Chunk Mesh 重建是瓶颈；且对底层渲染控制有限，后续做自定义 LOD/区块流式加载时要绕开很多封装。
> - **候选 B：Unreal Engine 5**。优点：Nanite/Lumen 视觉效果顶级。缺点：引擎体量巨大、C++ 宏/反射系统学习曲线陡，对"体素 + 每帧重建大量网格"的工作流并不自然，体积与编译时间对个人项目负担大。
> - **候选 C：Godot 4**。优点：开源轻量，GDScript 快速迭代。缺点：3D 性能相对弱，体素场景需要大量 GDExtension C++ 代码补性能，等于仍然在写引擎。
> - **结论**：本项目以"学习引擎底层 + 对体素做极致定制"为核心诉求，选 **C++ 自研引擎**。若目标是"快速出商业成品"，反而应该选 Unity。

### 1.3 目标硬件基线（性能验收前提）

§4 与 §7 的性能预算只有在**明确最低配置**之后才可验收。本项目以**中端独显**为基线：

| 项目 | 最低配置（基线） | 推荐配置 | 说明 |
| --- | --- | --- | --- |
| GPU | 同级 **GTX 1660 / 6 GB 显存**（或同级 AMD） | RTX 3060 / 8 GB+ | 显存是最先见底的资源，见 §4.1 内存估算 |
| CPU | 4 核 8 线程 | 6 核 12 线程 | 决定 Worker 线程数与区块生成吞吐 |
| 内存 | 8 GB | 16 GB | CPU 侧 24 区块视距约 70~150 MB，压力很小 |
| 分辨率 / 帧率 | **1920×1080 @ 60 FPS** | 1440p @ 60 FPS | 全文所有"60 FPS"均指此分辨率 |
| 图形基线 | **Vulkan 1.1+**（Windows 10 1903+） | — | SDL3_gpu 在 Windows 优先走 Vulkan，D3D12 为同平台备选后端 |
| 视距底线 | **16 区块**达 60 FPS | 24 区块达 60 FPS | 与 §8 V0.5 目标、§4.4 Draw Call 分档一致 |

**验收规则：**

- 性能验收必须在**基线配置**上测；推荐配置上的数据只作参考，不算达标。
- 任何突破 §4 / §7 预算的改动，必须同时给出**基线配置**上的 Tracy 数据。
- 若基线配置无法达标，优先调整 LOD 与区块卸载策略（§4.4），而不是放宽 §4.4 的 Draw Call 分档。

## 2. 总体技术架构分层

引擎采用**分层解耦**设计，从下到上依次为：

```
┌─────────────────────────────────────────────────────────┐
│  游戏逻辑层（Game Layer）                                │
│  玩法、数值、关卡、UI、AI —— 通过引擎 API 实现，与核心解耦 │
├─────────────────────────────────────────────────────────┤
│  体素世界层（Voxel World Layer）★ 本项目核心             │
│  区块分段 · 程序化生成 · 流式加载 · 体素光照 · 体素碰撞   │
├─────────────────────────────────────────────────────────┤
│  引擎核心层（Engine Core Layer）                         │
│  游戏主循环 · 渲染封装 · 输入 · 资源管理 · ECS · 内存管理 │
├─────────────────────────────────────────────────────────┤
│  平台抽象层（Platform Abstraction Layer）                │
│  窗口 · 图形 API · 音频 · 文件 IO · 多线程 · 计时器       │
└─────────────────────────────────────────────────────────┘
```

**设计原则：**

- 引擎核心层只提供通用能力，**不含任何具体游戏内容**。
- 游戏逻辑层与核心层完全解耦，便于后续用同一引擎开发第二款游戏。
- 平台抽象层隔离操作系统与图形 API 差异，为跨平台与后续扩展 Vulkan/DX12 留出接口（RHI）。
- 体素世界层**不直接调用平台 API**，只能通过引擎核心层与平台抽象层访问硬件——否则后续换 RHI 后端时会遍地硬编码。

## 3. 核心技术栈选型

### 3.1 编程语言与标准

| 项目 | 选型 | 选型理由 |
| --- | --- | --- |
| 语言 | **C++** | 游戏引擎行业事实标准，性能可控、底层控制力强、生态成熟；Unreal / Godot / 几乎所有商业 3A 引擎核心都使用 C++；方便直接对接 OpenGL/Vulkan/Jolt 等 C API 与 C++ 库 |
| 标准 | **C++17（主力），预留 C++20 升级路径** | C++17 提供 `std::optional`、`std::variant`、`std::string_view`、结构化绑定、`if constexpr`，足够覆盖引擎开发需求且三大编译器（MSVC/Clang/GCC）已全面支持；C++20 Modules/Concepts 能改善编译时间与接口约束，但 vcpkg 下部分三方库的 C++20 支持仍在过渡，**先用 C++17 保稳，子模块逐步试点 C++20** |
| 编译器 | **MSVC 2022（Windows 主开发），Clang（备用），GCC（Linux 验证）** | MSVC 调试体验（Edit and Continue、NatVis、可视化 STL 容器）在 Windows 下最强；Clang 报错信息更友好、跨平台行为一致，可作为 CI 第二编译器；GCC 为 Linux 默认选择 |

> **备选项：Rust**。Rust 的所有权模型天然规避 UAF/数据竞争，且已有 Bevy 这样优秀的 ECS 引擎；但游戏引擎生态（图形调试、物理、模型加载、跨平台打包）整体仍落后 C++ 一到两个身位，体素引擎开源参考（如 bevy_voxel）规模与成熟度远不及 C++ 生态。**个人项目若以"学习引擎底层 + 长期可维护"为目标，C++ 仍是更稳妥的起步选择**；若你本人已经非常熟悉 Rust，Bevy + 自研 voxel 插件是一条可行但资料更少的路。

### 3.2 引擎核心模块技术栈

#### 🎨 图形渲染（Rendering）

| 项目 | 选型 | 选型理由 | 备选项与对比 |
| --- | --- | --- | --- |
| 入门图形 API（★ 已统一定稿） | **SDL3_gpu（首选：现有高性能库 + 最低成本跑通）** | 直接复用 SDL3 自带的现代 GPU 抽象，**免手写交换链/渲染通道/同步的数百行样板**；运行时按平台自动选择 **Vulkan（Windows/Linux/Android）/ Direct3D 12（Windows）/ Metal（macOS/iOS）**；支持 Buffer/Texture/Pipeline/CommandBuffer 显式管理、多线程录制命令缓冲，且已内置 `SDL_DrawGPUIndexedPrimitivesIndirect`，为后续 MDI 合批留好接口。**代价**：① Shader 须离线编译为 SPIR-V/DXIL（用 SDL 官方 `SDL_shadercross` 或 glslc/dxc）；② 抽象粒度不如裸 Vulkan 细，bindless/mesh shader 等高级特性受限。**注意：SDL3_gpu 后端为 Vulkan/D3D12/Metal，不包含 OpenGL。** | **备选项 A：手写 OpenGL 3.3 Core（学习优先）**。优点：运行时编译 GLSL、**无需离线 Shader 工具链**，教程（learnopengl.com）最丰富，能亲手管理 VBO/VAO/Shader/FBO；缺点：属维护型 API、多线程录制不友好，且**代码量远高于 SDL3_gpu**。**备选项 B：OpenGL 4.5（DSA 路径）**，API 更现代但 macOS 最高仅 4.1。**结论（按本项目“低成本跑通 + 优先现有高性能库”原则）：首选 SDL3_gpu；仅当“亲手理解渲染管线”为第一诉求时选备选项 A，但应在 V0.4 前迁移到统一渲染接口，避免长期绑定维护型 API。** |
| 后期高性能后端 | **由 SDL3_gpu 覆盖（Vulkan / D3D12 / Metal）；仅在超出其能力时再手写 Vulkan 后端（V1.0 之后）** | 首选方案下这三个后端**已通过 SDL3_gpu 免费获得**，无需自己"接入"；仅当遇到抽象粒度不足的真实瓶颈（bindless texture、mesh shader、GPU-driven 管线）时，才通过渲染接口下沉到手写 Vulkan 后端。**接入时点统一为 V1.0 之后（与 §8 路线图一致）** | **不建议提前手写多后端**：抽象写太早属过度设计。**备选项：提前手写 Vulkan**——性能上限最高、参考最多（vkGuide、SaschaWillems），但仅初始化（交换链+渲染通道）就需数百行，对第一版引擎是工期杀手。**结论：V0.x 用 SDL3_gpu，V1.0 后按真实瓶颈决定是否手写 Vulkan。** |
| 数学库 | **GLM（OpenGL Mathematics）** | header-only，零依赖；向量/矩阵/四元数 API 与 GLSL 几乎一致，写 Shader 时不需要"脑内翻译"；行业事实标准，vcpkg 一键安装 | **备选项 A：自研数学库**。优点：完全可控、可做 SIMD 内联；缺点：四元数/矩阵求逆等边界 case 容易出 bug，调试成本高。**结论：V0.x 全用 GLM，等后续遇到真正 SIMD 热点（如 10 万+ 实体位置更新）再考虑局部替换。备选项 B：DirectXMath / Eigen**。DirectXMath 绑死 Windows；Eigen 偏科学计算，对游戏常见操作不便利。均不推荐。 |
| 窗口与上下文 | **SDL3** | SDL3 稳定版自 2025 年起发布并持续迭代（**3.4.0 发布于 2026 年 1 月**，Debian 已收录 3.4.x 包），相比 SDL2 重写了 GPU 抽象层（**SDL3_gpu，后端为 Vulkan / Direct3D 12 / Metal**）与音频 API（SDL3_audio），并整合手柄、高 DPI、IME；**一个库覆盖窗口 + 输入 + 音频 + GPU 抽象**，能少 3~4 个依赖 | **备选项 A：GLFW**。优点：极简、专注于窗口与输入，代码量小、编译快；缺点：没有音频/手柄/文件系统抽象，需要自己再引入一套音频库（如 miniaudio）。适合"想自己控制每个模块"的开发者。**备选项 B：Qt / wxWidgets**。通用 GUI 框架，重量大、事件循环与游戏主循环模型冲突，**不适合**。**结论：默认选 SDL3，一站式解决平台层；若你极度厌恶"库帮你做了太多事"，换 GLFW + miniaudio 组合。** |
| 纹理加载 | **stb_image** | 单头文件、零依赖、零构建成本；支持 PNG/JPG/BMP/TGA，覆盖体素游戏 99% 纹理需求 | **备选项：FreeImage / DevIL / libpng**。功能更多但依赖链长、编译复杂，对体素项目属于过度工程。 |
| 模型加载（方块实体/怪物） | **Assimp** | 支持 FBX/OBJ/glTF 等几乎所有 3D 格式；社区活跃、vcpkg 可直接装；后期加怪物模型、方块实体渲染时必需 | **备选项：直接用 cgltf（glTF 专用）+ 自写 OBJ 加载器**。轻量但格式覆盖少。**结论：V0.x 暂时不需要，等 V0.5 加怪物时再引入；不引入也不影响体素主流程。** |
| GPU 抽象层（RHI） | **SDL3_gpu 直接作为 RHI（首选：零自研成本）** | 直接以 SDL3_gpu 作为渲染后端抽象，**省掉"自研 RHI"的全部工作量**，是"最低成本跑通"的路径；引擎侧只需包一层薄薄的项目接口（`Renderer` / `MeshBuffer` / `Material`），便于日后替换后端而不动上层 | **备选项：自研薄抽象 RHI**。只抽象 `Buffer / Texture / Shader / Pipeline / CommandBuffer` 几个核心对象，底层直接实现 SDL3_gpu；优点：粒度可控、不被 SDL3_gpu 限制；缺点：多写一层代码，过早抽象易过度设计。**建议：V0.x 直接用 SDL3_gpu；当抽象粒度不足（bindless / mesh shader）时，再在同名接口下替换实现。** |

#### ⏱️ 主循环与时间步

| 项目 | 选型 | 选型理由 | 备选项与对比 |
| --- | --- | --- | --- |
| 主循环模型 | **固定时间步长（Fixed Timestep）+ 渲染插值** | 逻辑/物理以固定 `dt`（如 1/60 s）推进，渲染帧之间用插值系数平滑。这是体素游戏**碰撞确定性**的前提——§4.5 的子步进与自动上台阶都假定 `dt` 固定；若用可变 `dt`，高速移动的隧穿判定与跳跃手感会随帧率漂移（60Hz 与 144Hz 表现不同） | **备选项：纯可变时间步长**。实现最简单，但物理/手感随帧率变化，且不利于确定性生成与后续联机。**结论：固定步长 + 累加器（accumulator）+ 渲染插值；并限制单帧最大补步数（如 ≤5），防止卡顿后的"死亡螺旋"。** |
| 时间源 | **SDL3 高精度计时（`SDL_GetPerformanceCounter` / `SDL_GetPerformanceFrequency`）** | 与 SDL3 统一，零额外依赖；单调时钟，不受系统校时影响 | **备选项：`std::chrono::steady_clock`**。同为单调时钟，可行；**不使用 `system_clock`**（会被系统时间调整影响）。 |

#### 🧱 架构与内存管理

| 项目 | 选型 | 选型理由 | 备选项与对比 |
| --- | --- | --- | --- |
| 架构模式 | **ECS（Entity-Component-System）** | 组合优于继承，避免"Entity → LivingEntity → Mob → Monster → Zombie"这种继承爆炸；数据按组件类型连续存储，CPU 缓存命中率高，体素世界里上千个怪物、掉落物、粒子天然适合批量处理 | **备选项 A：传统组件模式（GameObject + Component 指针链表，类似 Unity）**。优点：易理解；缺点：组件内存离散、每次虚函数调用都跳指针，批量更新性能差。**备选项 B：纯 OOP 继承树**。体素游戏实体种类多（方块、怪物、掉落物、弹射物、载具），继承树会迅速膨胀，不可维护。**结论：ECS 是现代游戏引擎的主流选择，选 ECS。** |
| ECS 实现 | **自研稀疏集（Sparse Set）ECS** | 体素项目 ECS 只需要管理玩家、怪物、掉落物、粒子这类**动态实体**（数量级万级），不需要管理方块（方块是区块内数组，绝不放 ECS）。EnTT 功能强大但学习曲线陡、编译时间长；自研一个支持稀疏集 + 类型擦除视图的轻量 ECS 代码量约 1000~2000 行，完全可控 | **备选项：EnTT**。header-only、工业级、性能极高（Minecraft 社区多个项目在用）；缺点：模板代码极重，编译时间显著增加，错误信息几乎不可读；对单人项目，出 bug 调试成本高。**建议：V0.1 可直接用 EnTT 快速起步，V0.4 之前评估是否切换到自研（那时你已清楚自己用了 EnTT 百分之几的功能）。** |
| 所有权管理 | **`std::unique_ptr` 为主，`std::shared_ptr` 仅用于跨系统共享资源** | `unique_ptr` 零开销、所有权明确，适合 Engine、ChunkManager、Renderer 这类"有唯一拥有者"的对象；`shared_ptr` 有原子引用计数开销，不应滥用 | **备选项：裸指针 + 手动 new/delete**。性能最高但极易泄漏/悬垂，现代 C++ 项目不推荐；**只有在热路径、自定义分配器管理的内存里才允许裸指针持有**，接口层仍用智能指针。 |
| 自定义分配器 | **对象池（Object Pool）+ 线性分配器（LinearAllocator）** | 对象池复用子弹、粒子、掉落物等高频创建销毁对象，避免堆碎片；线性分配器用于每帧临时数据（如构建中的网格顶点数组、culling 结果），帧末一次性重置，零碎片、极快 | **备选项 A：全用 `std::vector::reserve` 复用容器**。部分场景可行，但语义不如专用分配器清晰。**备选项 B：jemalloc / mimalloc 替换系统 malloc**。对大块分配有提升，但体素项目真正的热路径还是对象池和栈/线性分配。 |
| 坐标类型 | **BlockPos 用 `int32`，WorldPos 用 `double`** | 单精度浮点在距离原点 2^24 格（约 1600 万格）时精度降到 1 格以下，超大世界会出现"远处方块抖动"；玩家/相机世界坐标必须用双精度，上传给 GPU 时再做"相对相机偏移"（Camera-Relative Rendering）转为单精度 | **备选项：全用 `float`**。距离玩家 8192 格外就会出现明显抖动，对超大世界不可接受。**备选项：全用 `int64`**。渲染管线需要浮点，转换成本高、Shader 端不自然。**结论："存储用 double、渲染时相对化"是业界标准做法。** |

## 4. 体素超大世界专属核心模块

> 这部分是类《我的世界》游戏与普通 3D 游戏的**核心区别**，也是实现"超大、随机生成"的关键。

### 4.1 体素数据与区块架构（核心中的核心）

**分块分段存储，从根源避免内存爆炸：**

- 世界按 **区块（Chunk）** 组织，区块水平尺寸固定 **16×16**，高度 **384**（可按需扩到 512）。
- 区块内部进一步切成 **16×16×16 的 Section（子段）**——这是存储/网格构建/光照的最小单元。
- 每个 Section 内的方块 ID 使用 **调色板（Palette）压缩**：
  - 区块内实际出现过的方块类型通常只有几种（石头、泥土、空气、矿石……），无需给每个方块分配 `uint16`；
  - 用一个 `vector<BlockId>` 存"本 section 用到的方块"，再用每方块 4~8 bit 索引到调色板；
  - 空气占绝大多数的 section 使用 **空 section（nullptr）标记**，不分配任何内存。
- 方块属性（是否透明、是否固体、纹理坐标、硬度、发光等级、摩擦系数）统一存入全局 `BlockRegistry`（方块注册表），不随方块重复存储，注册表在启动时一次性构建。
- **BlockEntity（方块实体）**：箱子、熔炉、告示牌、漏斗等"方块 ID 之外需要附加数据"的方块，单独挂在 Chunk 上的 `unordered_map<BlockPos, BlockEntity*>`，每 Chunk 通常只有个位数。
- **内存估算（以 16×384×16 区块、24 区块视距为例，分列 CPU 内存与显存）**：
  - 加载区块数：(2×24+1)² = **2401 个**；
  - 每区块方块数据（section 压缩 + palette）：平均约 8~20 KB（而非 96 KB 满分配）→ **CPU 侧合计约 19~48 MB**；
  - 每区块光照数据：`16×16×384 = 98,304 方块 × 1 字节（2 nibble）= **96 KB 未压缩**`（原稿此处按 48 KB 计，少算一倍）；天空光在露天段恒为 15、压缩率很高，地下/过渡段较难压缩，**按平均压到 20~40 KB 估算** → **CPU 侧合计约 48~96 MB**；
  - 每区块网格数据（顶点 + 索引）平均 50~200 KB（视地形密度）→ **合计 120~480 MB，这部分常驻显存（VRAM）而非系统内存**；纹理数组另计（视层数，通常 32~64 MB）；
  - **总计：CPU 内存 ≈ 70~150 MB；显存 ≈ 150~550 MB**。系统内存压力很小，**真正需要盯的是 VRAM**——4~6 GB 的中低端 GPU 在 24 区块视距下会先于内存见底，这也是 §4.4 的 LOD 与区块卸载策略的主要约束。
- **结论**：没有 section 分段 + palette 压缩，要撑住 24 区块视距基本不可能——这是 V0.1 就必须做的设计决定。

**网格优化（决定帧率上限）：**

- **面剔除（Face Culling）**：只生成"相邻是空气/透明方块"的可见面；V0.1 必做。
- **贪婪网格化（Greedy Meshing）**：合并**同材质、同朝向、且 4 个角的天空光/方块光/AO 完全一致**的连续面为大四边形，面数进一步压缩 3~10 倍；**V0.2 必须做**（不要等到 V0.5，否则顶点格式/数据结构要整体重写）。
- **贪婪合并的两条硬约束（关键，须在 V0.2 定稿）**：
  - **作用域 = 单个 Section**：因顶点位置用 uint8（0~16），**不跨 Section 合并**，否则位置溢出。
  - **合并判据必须预留 AO**：§4.6 的 AO 属**逐顶点**量，一旦 V0.5 开启，等价条件就须包含"4 角 AO 相同"，否则要么无法合并、要么 AO 结果错误。**因此 V0.2 写 Greedy 时就把判据定为"材质 + 朝向 + 4 角光照/AO 一致"，AO 先恒为 0 占位**；V0.5 只需填入真实 AO，无需重写网格器。
- **顶点格式**：位置（uint8 × 3，区块内相对坐标）+ 光照（uint8，天空光高 4 位 + 方块光低 4 位）+ 纹理 UV（uint8 × 2）+ 法线/朝向（uint8），单顶点 8 字节，比 32 字节的传统 `float*3 + float*2 + float*3` 小 4 倍，GPU 带宽直接省 75%。
- **UV 平铺约定（必读）**：贪婪网格合并出的大四边形需要**重复平铺**纹理（1×N 格），因此 UV **不能**只存 0~1 的归一化值，否则纹理会拉伸。约定：顶点存"格子内 UV（0~1，uint8 归一化）" + "该四边形跨的格数（quadSize）"，Vertex Shader 输出 `uv * quadSize`，Fragment Shader 用 `fract()` 采样。**此约定必须在 V0.2 写 Greedy 之前固定，否则顶点格式要重写。**

> **备选项：Culled Meshing + 简单 quad，不做 Greedy**。优点：实现简单；缺点：顶点数多 3~10 倍，渲染距离一旦上 16 区块就顶点数爆炸。**结论：Greedy 必做，不是可选优化。**

### 4.2 程序化随机生成系统

**基础噪声层（FastNoiseLite）：**

- 2D Simplex/Perlin 噪声叠加（大陆性噪声 + 丘陵噪声 + 细节噪声）→ 地表高度图。
- 3D Perlin/Worley 噪声 → 地下洞穴、矿脉、溶洞、含水层。
- 2D 温度 + 湿度噪声 → Biome 映射（雪原 / 沙漠 / 森林 / 丛林 / 海洋 / 山地），与高度图解耦，避免"山顶出现沙漠"。

> **噪声库选型**：**FastNoiseLite**（header-only，C++ 单头文件，支持 Simplex/Perlin/Worley/Cellular 等所有常用噪声，性能极高，vcpkg 可装，也可以直接 vendoring 进 `third_party/`）。
> - **备选项 A：libnoise**。老牌但久未维护，API 笨重。
> - **备选项 B：自研噪声**。Perlin/Simplex 代码量不大但易出"网格伪影"等边界 bug，初期不值得造轮子。

**结构生成层：**

- **采用分块确定性网格抖动（Chunked Jittered Grid）**——它满足"只看当前区块 + 种子即可重建"这一流式加载的硬约束：
  1. 世界按"结构单元格"划分网格（如村庄 32×32 区块一格、树木 2×2 区块一格）；
  2. 对每个格子，用 `hash(seed, gridX, gridZ)` 决定"是否生成结构"以及"格子内的偏移位置（jitter）"；
  3. 在该格子对应区块生成时，确定性地计算出结构位置，再按结构模板放置方块；
  4. 跨区块的大型结构（村庄）由"主区块"负责生成，相邻区块直接读取结果。
- 由此保证**任意区块都能独立按种子重建**，与流式加载完全兼容；结构分布均匀度略低于理论最优，但体素游戏完全够用。
- **约束**：结构生成只依赖"当前区块坐标 + 全局种子"，不依赖任何全局可变状态（否则区块无法独立重建）。

**种子与确定性：**

- 所有生成逻辑（噪声、结构、植被、矿石）都基于全局 64-bit 种子派生（用 `splitmix64` 或 `xxhash` 派生各子系统的种子，避免噪声间耦合）。
- **确定性要分两个层级（重要，原稿"永远一致"表述不严谨）**：
  - **同一构建内确定性（必要，单机即依赖）**：同一份可执行文件 + 同一种子 → 生成结果逐方块一致；未被玩家修改的区块**无需存盘**，走到对应位置按种子重新生成即可。前提是生成逻辑**禁止依赖 `rand()`、时间、线程调度顺序、容器迭代顺序**。
  - **跨平台 / 跨版本确定性（联机或"共享种子"才需要）**：FastNoiseLite 为 **float 实现**，不同编译器、FMA 收缩、优化等级下结果可能不同，因此**不能承诺"跨平台永远一致"**。若后续要做确定性联机，需改用**整数哈希噪声**（整数域运算，无浮点差异）。
- 玩家修改过的区块标记为"脏区块"，写入磁盘并在区块生成时覆盖默认生成结果。

### 4.3 超大世界流式加载系统

- **视距管理**：以玩家为中心，按曼哈顿/切比雪夫距离维护 `(2*viewDistance+1)^2` 个已加载区块；超出距离的区块卸载、释放内存。
- **加载优先级**：按"玩家当前列 → 玩家面向方向前方 → 其他已加载区"三级队列调度，保证玩家面前不出现空洞。
- **多线程异步任务系统**：**首选现成的高性能任务图库 enkiTS 或 Taskflow**（原生支持依赖计数与工作窃取，零自研成本），分阶段任务：
  1. **生成阶段**（后台线程）：按种子生成方块数据；
  2. **光照阶段**（后台线程）：BFS 光照传播，注意跨区块边界；
  3. **网格阶段**（后台线程）：贪婪网格化，产出顶点/索引缓冲上传命令；
  4. **上传阶段**（必须主线程）：把顶点/索引缓冲上传到 GPU（SDL3_gpu：`SDL_UploadToGPUBuffer`；OpenGL 备选：`glBufferData`）；
  5. **卸载阶段**（后台线程）：序列化脏区块到磁盘，释放内存。
- **依赖调度（新增，关键）**：区块的网格构建**必须等所有邻居区块生成完毕**才能处理边界面。任务调度需要"区块依赖图"——生成时若邻居未就绪，把自己加入邻居的"待通知列表"；邻居就绪后再触发本区块的网格任务。
- **双缓冲区块数据**：主线程渲染只读"当前版本"的区块网格，后台生成"新版本"，上传完成后原子指针交换，避免读写竞争。

> **多线程模型对比**：
> - **首选：直接套用 TaskFlow / enkiTS**。现成的现代任务图库，支持依赖计数与工作窃取，**零自研成本**，符合"低成本跑通 + 优先现有高性能库"原则。**推荐。**
> - **备选项 A：自研无锁线程池 + 工作窃取（Work Stealing）**。最灵活、可裁剪，实现约 300 行；缺点是依赖图与唤醒逻辑易出竞态 bug（须用 TSan 验证），属"造轮子"。适合以学习为目的。
> - **备选项 B：`std::async` / 每任务一线程**。实现最简单，但线程数不可控、频繁创建销毁开销大，**不推荐**。
> - **与 Jolt 共享线程池的时序（原方案漏洞修正）**：Jolt 到 **V0.4** 才引入，而任务系统在 **V0.3** 就要用——**V0.3 阶段无 Jolt 可复用**，必须使用 TaskFlow/enkiTS（或自研）；**V0.4 引入 Jolt 后，再评估把 Jolt 的 JobSystem 桥接到同一线程池**，避免线程数翻倍。

### 4.4 体素专属渲染优化

- **纹理数组（Texture Array）★ 优先于纹理图集**：把所有方块面纹理放进一张纹理数组（**SDL3_gpu：多层 `SDL_GPUTexture`**；OpenGL 备选方案：`GL_TEXTURE_2D_ARRAY`），每层一个 16×16 纹理。
  - **为什么不用纹理图集（Atlas）**：图集在开启 mipmap 时会出现**纹理渗色（bleeding）**——相邻方块的纹理在低 mip 层混在一起，远处方块出现杂色；需要 1~2 像素 padding 缓解但仍不彻底。纹理数组每层独立 mipmap，无此问题，且 Shader 里用 `(uv, layer)` 采样比图集坐标计算更直观。
  - **结论**：SDL3_gpu 原生支持纹理数组，**V0.1 直接使用 Texture Array**（无需先用图集过渡）；即便走备选手写 OpenGL 方案，纹理数组在 GL 3.0+ 也可用。
- **Draw Call 合批**：每区块的可见面合并为一个 VBO+IBO，非透明方块一个 draw call，透明方块（水、玻璃）单独一个 draw call 并按距离排序。**目标值必须与视距匹配**：24 区块视距下共 2401 个区块，即便视锥 + 遮挡剔除后仍约 600~800 个可见区块，连同透明通道约 **1200~1600 draw call**——因此现实目标定为 **"≤1500/帧（视距 16 时 ≤700）"**，而非"几百"。**若要把 draw call 真正压到几百**，备选方案是 **Multi-Draw Indirect（MDI）+ 4×4 区块区域合批**（SDL3_gpu 已提供 `SDL_DrawGPUIndexedPrimitivesIndirect`），但实现复杂度显著上升，列为 V0.5 之后的优化备选项。
- **LOD（细节层次）**：
  - 普通距离（0~8 区块）：完整贪婪网格；
  - 中距离（8~16 区块）：2×2×1 合并网格（每 2×2×1 格合为一个面）；
  - 远距离（16~32 区块）：4×4×2 合并网格或直接用高度图生成的 Impostor 面片；
  - 超远（>32 区块）：可选 Impostor 贴图（预渲染的远景地貌图）。
- **视锥体裁剪（Frustum Culling）**：用区块 AABB 在 CPU 侧做视锥剔除，视野外区块不提交 draw call；加上 occlusion culling（遮挡查询）效果更好，V0.5 再加。
- **面排序与透明**：水体、玻璃等半透明方块单独建网格，渲染时按"从远到近"排序；或用 order-independent transparency（后期再做）。
- **天空 / 雾**：指数雾与天空色混合，远距离方块融入天空色，既提升氛围又隐藏 LOD 切换跳变。

### 4.5 体素专属物理优化（关键修正）

- **自研 AABB 体素碰撞**：只查询玩家/实体包围盒周围 **3×3×3 个方块**（单位是**方块**而非 section——1 个 section = 4096 个方块，那样查询范围会大到毫无意义）内的固体方块做**扫掠 AABB（Swept AABB）**检测，速度比通用物理引擎快上百倍。
- **子步进（Sub-stepping）**：玩家速度高时单帧位移超过 1 格会导致"隧穿"，把 §3.2 的固定时间步 `dt` 切分成若干 ≤ 0.25 格位移的子步，每步分别做 X/Y/Z 三轴碰撞解算，避免穿墙。
- **自动上台阶（Step-up）**：碰到 1 格高的障碍时，自动把玩家抬起 1 格测试是否可站立，可站立则平滑上台阶——**这是体素游戏"不卡边"手感的核心，而不是缩小碰撞盒**。
- **碰撞盒尺寸**：体素游戏的玩家碰撞盒是精确尺寸（如宽 0.6、高 1.8、眼高 1.62，与 MC 一致），**不要缩小碰撞盒来"提升手感"**——这会导致掉进一格小洞、方块边缘站不稳。体素游戏解决手感靠的是 sub-stepping + step-up + 正确的 slope limit，而不是缩小碰撞盒。
- **通用物理引擎（Jolt）只用于**怪物、掉落物、弹射物、矿车等动态刚体；这些实体的物理查询通过回调到体素世界接口（`IsBlockSolid(x,y,z)`）完成，不把体素喂给 Jolt 当网格。

### 4.6 体素光照系统

- **光照数据存储**：每方块存储 2 个 nibble（共 1 字节）——高 4 位天空光（0~15），低 4 位方块光（0~15）；光照跟随 section 压缩存储。
- **天空光**：从世界顶部（或 section 顶部）向下传播，遇到不透明方块停止；天空光值 15 表示露天，0 表示完全遮挡。
- **方块光**：火把 14、岩浆 15、萤石 15 等光源，向 6 邻域 BFS 传播，每格衰减 1；在空气/透明方块中传播。
- **BFS 增量更新**：区块加载或方块修改时，不做全量重算，而是以"被改变的光源/被移除遮挡的位置"为起点 BFS 传播；注意跨区块边界的光照传播（当邻居区块尚未加载时暂挂，邻居就绪后继续）。
- **顶点颜色打包**：光照强度打在顶点颜色的 RGB 通道（天空光 + 方块光取 max，乘以全局亮度曲线），Shader 内与纹理采样结果相乘。
- **光照重网格问题**：光照值在顶点色里意味着每次光照变化（火把放置/破坏）都需要重建该区块网格。这是 MC 的经典性能热点，**V0.4 之后可以改为"光照作为独立顶点属性"或把光照计算移到 Shader 做三线性采样**，避免小范围光照变化导致整区块网格重建。
- **环境光遮蔽（AO）**：V0.5 启用——在 mesh 构建时根据相邻方块计算每顶点 AO 系数（0~3），打在顶点 Alpha 通道。**注意**：AO 的合并判据必须在 §4.1 的 V0.2 Greedy 阶段就以"占位恒为 0"预埋，否则开启 AO 时会破坏贪婪合并或产生错误 AO。

### 4.7 高效序列化存储

- **序列化方案：自写二进制 + zstd 压缩**。
  区块数据本质是固定布局的字节数组 + 压缩，**自己写序列化代码只需几十行**（写 magic、写版本、写方块 ID 数组、写光照数组、写 palette、写 block entity 列表），格式完全可控、零模板膨胀、无第三方依赖。
- **格式设计**：区域文件（参照 MC `.mca` 格式），每个 `.voxr` 文件存 32×32 个区块：
  - 文件开头是 1024 个区块位置表（offset + size），支持随机读；
  - 每个区块独立使用 **zstd**（或 zlib）压缩方块数据 + 光照数据 + palette + block entity 列表；
  - 压缩前单区块约 10~50 KB，压缩后通常 <5 KB。
- **`.voxr` v1 字段规格（冻结；变更须走版本迁移）**：

  区域文件头（前 8208 字节为固定头）：

  | 偏移 | 字段 | 类型 | 说明 |
  | --- | --- | --- | --- |
  | 0 | `magic` | `char[4]` | `"VXR1"` |
  | 4 | `formatVersion` | `uint16` | 当前 = 1；不匹配即触发迁移 |
  | 6 | `generatorVersion` | `uint16` | 生成算法版本，影响未修改区块的重建结果 |
  | 8 | `regionX` / `regionZ` | `int32` × 2 | 本文件覆盖的区域坐标 |
  | 16 | `chunkTable[1024]` | `{uint32 offset, uint32 size}` × 1024 | 32×32 区块位置表；`offset = 0` 表示该区块缺省 |
  | 8208 | 区块数据区 | — | 每区块独立 zstd 压缩 |

  单区块**压缩前**载荷（小端序）：

  | 顺序 | 字段 | 说明 |
  | --- | --- | --- |
  | 1 | `chunkX` / `chunkZ` | `int32` × 2，用于校验位置表未错位 |
  | 2 | `sectionMask` | `uint32`，24 个 bit 标记哪些 Section 非空 |
  | 3 | Sections | 仅存 `sectionMask` 命中的 Section；每个含 `paletteSize`、`palette[]`、位打包方块索引 |
  | 4 | `lightSections` | 与 Sections 同结构；每方块 1 字节（高 4 位天空光 / 低 4 位方块光） |
  | 5 | `blockEntityCount` + 列表 | 各含 `BlockPos`(3×`int32`)、`typeId`(`uint16`)、长度前缀载荷 |
  | 6 | `payloadCrc32` | `uint32`，压缩前载荷校验和 |

  **规则**：字段顺序与宽度一经冻结，任何变更都必须提升 `formatVersion` 并配套迁移函数与迁移测试（见 §9.3）。
- **压缩库**：**zstd**（Facebook 开源，比 zlib 快 3~5 倍、压缩率更好；单文件 amalgamation 可直接 vendoring）。
- **IO 策略**：
  - 脏区块**延迟批量写盘**（每 5~10 秒 flush 一次，玩家退出前强制 flush）；
  - 读盘走内存缓存（LRU 缓存已读区块），避免同一区块重复读；
  - 纯异步 IO（`std::thread` + 停止标志，或统一交给 §4.3 的任务系统线程池；**不使用 C++20 的 `std::jthread`，与 §3.1 的 C++17 主标准保持一致**），主线程永远不阻塞在磁盘。
- **存档元数据**：单独写 `level.dat`（JSON 或简单二进制），存种子、玩家位置、生成版本号，用于版本兼容。
- **版本迁移（强制）**：每个 `.voxr` 区块与 `level.dat` 头部必须含 `version` 字段；**任何字段或布局变更都必须配套迁移函数与迁移测试**（"旧档能被新版本正确读出"），否则玩家存档会静默损坏。

> **学习参考**：开源 C++ 体素引擎 **Minetest** 的区块管理、生成逻辑、光照 BFS 值得阅读源码学习；**Terasology**（Java）的架构设计也可参考。本项目目标是自研引擎以获得完整架构掌控力，因此这些项目**作为设计参考来源**即可（本项目从零自研，不做二次开发）。

## 6. 引擎与游戏的接口设计

### 6.1 脚本系统绑定（V1.0 之后引入）

| 选型 | 理由 |
| --- | --- |
| **Lua 5.4 + sol2** | Lua 解释器极小（几百 KB）、启动快、热重载友好，是游戏行业事实标准（Minecraft mod、Roblox、World of Warcraft 都用 Lua）；sol2 是现代 C++/Lua 绑定库（header-only），支持 C++17，API 直观，比 LuaBridge/LuaBind 活跃且类型安全 |

> **备选项对比**：
> - **Python + pybind11**：优点是语言熟悉；缺点：解释器几十 MB、启动慢、分发 exe 大、GC 停顿不可控，不适合游戏主逻辑。
> - **C#（Mono）**：类似 Unity 的做法；需要嵌入 Mono 运行时，工作量大，单人项目不划算。
> - **Wren / AngelScript / ChaiScript**：小众脚本语言，生态小、文档少、踩坑难以求助。
> - **自研 DSL/可视化脚本**：工作量巨大，V2.0 之后再考虑。
> - **结论**：Lua + sol2 是最务实的选择；**V0.x 阶段不引入脚本**，游戏逻辑先用 C++ 写，等 API 稳定后再绑 Lua 做玩法迭代。

### 6.2 资源管理系统（Asset Manager）

- **异步加载**：所有资源（纹理、网格、音效、Shaders）通过 `AssetManager::LoadAsync<T>()` 返回 `shared_future<T*>`，后台线程加载、主线程可用。
- **引用计数**：`AssetPtr<T>` 本质是带引用计数的句柄，归零自动卸载（或进入 LRU 队列延迟卸载）。
- **热重载（Hot Reload）**：文件系统 watcher（SDL3 提供目录监视 API，或用 inotify/ReadDirectoryChanges）检测资源文件变更，自动重载 Shader/纹理/Lua 脚本；开发期改 Shader/纹理不用重启游戏。
- **支持格式**：纹理（.png/.jpg/.dds，BCn 压缩在加载时离线做一次）；模型（.glb/.gltf 通过 Assimp）；音频（.wav/.ogg，SDL3 内置）；Shader（.glsl，自写 include 预处理，并经 SDL_shadercross 离线编译为 SPIR-V 供 SDL3_gpu 使用）。
- **资源打包（V1.0+）**：发布时把 assets/ 打包成自定义 `.pak` 文件（简单的"文件名 → 偏移/大小/CRC"表 + zstd 压缩），减少小文件 IO。

### 6.3 场景编辑器（Editor）

- **Runtime 与 Editor 分离**：编译出两个目标——`game.exe`（纯 Runtime，无编辑器代码）与 `editor.exe`（链接 Runtime + Editor 模块）；Editor 层通过引擎公共 API 操作世界，不侵入 Runtime。
- **初期（V0.4）**：用 Dear ImGui 搭运行时调试面板（区块计数、帧时间、内存、玩家位置、放置方块作弊面板）。
- **中期（V0.6）**：加 Gizmo（可直接用 ImGuizmo）做物体放置、区块 inspector、实体列表、资源浏览器。
- **长期（V1.0+）**：场景序列化（JSON 或二进制）、关卡编辑器、Block Inspector（编辑 BlockRegistry 属性）。

## 7. 性能红线与常见致命坑

下表左列是**需识别并绕开的写法**，右列是**必须执行的做法**——执行与评审时以右列为准。

| # | 需绕开的写法 | 必须执行 |
| --- | --- | --- |
| 1 | ❌ 把每个方块做成独立 ECS Entity | ✅ **区块作为 Entity（甚至不进 ECS），方块是 Chunk Section 内数组里的数值**；仅动态物体（玩家/怪物/掉落物/弹射物/粒子）为独立 Entity |
| 2 | ❌ 主线程同步加载/生成区块 | ✅ 所有 IO、生成、光照、网格构建全丢后台线程；主线程只做渲染与输入，上传 GPU 才回主线程 |
| 3 | ❌ 每个方块单独 VBO/单独绑定纹理 | ✅ 每区块合批为一个 VBO+IBO，用 Texture Array；非透明方块一个 Draw Call，透明方块一个 Draw Call；**Draw Call 目标 ≤1500/帧（24 区块视距），要压到"几百"须上 MDI + 区域合批（见 §4.4）** |
| 4 | ❌ 持久化所有区块到磁盘 | ✅ 只存玩家修改过的脏区块；未修改区块靠种子确定性重生成；区域文件用 zstd 压缩 |
| 5 | ❌ 用通用物理引擎处理方块碰撞 | ✅ 自研 AABB Swept 体素碰撞 + 子步进 + 自动上台阶；Jolt 只用于动态刚体 |
| 6 | ❌ ~~碰撞盒缩小 20% 提升手感~~（原版错误建议） | ✅ 碰撞盒用精确尺寸（0.6×1.8），"手感宽容"靠子步进 + 自动上台阶 + 边缘检测实现；缩小碰撞盒会导致掉洞/穿模 |
| 7 | ❌ 遍历时删除实体/区块 | ✅ 标记清除法（mark & sweep），遍历后统一清理；或用双缓冲 swap |
| 8 | ❌ 高频对象（子弹/粒子/掉落物）频繁 new/delete | ✅ 对象池预分配 + 句柄（Handle）引用，避免堆碎片 |
| 9 | ❌ 全世界坐标用 `float` | ✅ 世界坐标用 `double`，渲染时做 Camera-Relative 偏移转 `float` 传 GPU |
| 10 | ❌ 区块生成不考虑邻居依赖就直接建网格 | ✅ 建网格前必须等邻居生成完成（任务依赖图/回调通知） |
| 11 | ❌ 结构生成依赖全局状态，无法只看当前区块重建 | ✅ 分块确定性网格抖动（Chunked Jittered Grid），保证区块独立可重建 |
| 12 | ❌ 用纹理图集 + mipmap 不做 padding | ✅ 优先用 Texture Array；若用图集至少留 2~4 像素 padding 防 bleeding |
| 13 | ❌ 每帧全量重算光照 | ✅ BFS 增量传播，仅在方块修改时局部更新 |
| 14 | ❌ 单线程做区块生成/网格 | ✅ Job System 多线程并行，注意线程安全与原子交换 |
| 15 | ❌ Debug 构建裸跑不开 sanitizer | ✅ Debug 配置默认开启 ASAN/UBSAN（Windows 用 ASAN，Linux/Clang 加 TSan），内存/竞态 bug 早发现 |
| 16 | ❌ 用可变 `deltaTime` 直接驱动物理与角色逻辑 | ✅ 固定时间步长更新逻辑 + 渲染插值（见 §3.2）；子步进与自动上台阶都依赖固定 `dt`，否则手感随帧率漂移 |
| 17 | ❌ 生成逻辑依赖 `rand()` / 时间 / 线程调度顺序 | ✅ 纯确定性函数（种子 + 整数坐标），保证同种子世界可复现；跨平台联机需改用整数哈希噪声 |

### 7.1 固定基准场景（性能对比的前提）

没有可重复的场景，Tracy 数据就无法跨时间对比，性能门禁形同虚设。以下协议**冻结**，任何性能对比都必须在此场景下进行：

| 项目 | 固定值 |
| --- | --- |
| 世界种子 | `0x5EED0001`（固定常量） |
| 玩家位置 | 出生点 `(0.5, 高度图高度 + 2, 0.5)`，朝向 +Z |
| 相机 | FOV 70°，近平面 0.05，远平面 `viewDistance × 16` |
| 视距档位 | **8 / 16 / 24 区块** 三档，分别记录 |
| 预热 | 全部区块达到 `Ready` 后再静置 **5 秒**，才可开始采样 |
| 采样 | 静止 10 秒 + 匀速直线前进 10 秒，各记录一条帧时间曲线 |
| 记录指标 | 帧时间 P50 / P95 / P99；draw call 峰值；常驻 CPU 内存；常驻 VRAM；Worker 线程利用率 |
| 工具 | Tracy（CPU / GPU zone + 内存）；RenderDoc 仅用于排查异常帧 |
| 场景约束 | 出生点周围 3×3 区块内不放置随机结构，保证跨版本可比 |

**规则**：报告必须写明「基线配置 / 视距档位 / 是否开启 LOD」三项，缺一即不可比。

## 8. 分阶段落地路线图

> 原则：**不要一开始就做"超大世界"**，每阶段都要有可运行可演示的产出。

### V0.1 最小闭环（预计 2~3 周）

- **1 个 Section（16×16×16）** 的体素渲染（作为未来 section 存储的基础单元，避免 V0.1 尺寸和后续架构不一致）。
- 实现**面剔除**（先做朴素 culled meshing，greedy 留到 V0.2）。
- 放置 / 破坏方块 + 射线检测（DDA 算法）。
- 玩家自由视角 + WASD 走动、跳跃、重力 + 自研 AABB 碰撞（不接 Jolt）。
- 技术栈：CMake + SDL3（窗口 + 输入 + **SDL3_gpu 渲染**）+ GLM + stb_image + Dear ImGui 调试面板；Shader 用 SDL_shadercross 离线编译为 SPIR-V。
- **固定时间步长主循环 + 渲染插值**（见 §3.2），以及极简 CVar/调试控制台（传送、切视距、暂停区块更新）。
- 里程碑：能在一个 16×16×16 的方块堆里飞来飞去、放块拆块。
- **验收标准（V0.1 完成判据，逐项可测）**：

  | 维度 | 可观察现象 | 量化指标 |
  | --- | --- | --- |
  | 渲染 | 屏幕出现一个 16×16×16 方块堆，可见面正确、无破面 | 基线配置 1080p ≥ 60 FPS |
  | 面剔除 | 方块堆内部面未被提交 | 单测断言内部面数 = 0；RenderDoc 截帧该堆仅 1 个 draw call |
  | 视角与移动 | 鼠标准星自由转动；WASD 走动、跳跃受重力约束 | 跳跃高度与 §1.3 基线无关地恒定 |
  | 射线检测 | 视线命中方块并被高亮 | DDA 命中 ≤ 5 格内方块，无误判 |
  | 放置 / 破坏 | 左键破坏、右键放置，立即反映到画面 | 操作后 ≤ 1 帧内网格更新完成 |
  | 碰撞 | 无法穿墙；可在 1 格台阶上自动上步 | 以 20 格/秒冲刺不穿墙（子步进生效） |
  | 时间步 | 逻辑行为与帧率无关 | 锁 30 FPS 与 144 FPS 时跳跃高度一致（误差 < 1%） |
  | 坐标精度 | 远离原点不抖动 | 相机移至 x = 10,000,000，方块边界无抖动 |
  | 调试设施 | ImGui 面板显示帧时间 / 区块数 / 玩家坐标；CVar 可切视距与暂停区块更新 | 面板可开关且不崩溃 |
  | 工程门禁 | 一键构建、零警告、测试与门禁全通过 | `cmake --preset debug` 单命令成功；`ctest --preset debug` 全绿；门禁脚本退出码 0 |

### V0.2 基础世界（预计 3~4 周）

- 引入 Chunk / Section 结构（16×16×16 section 组合为 16×64×16 世界，后续再加高）。

### V0.4 完善生成（预计 4~6 周）

- 叠加多层噪声：3D 噪声生成洞穴、含水层、矿脉；温度+湿度 Biome 映射。

- 物品栏、方块选择、十字准星、基础 HUD（Dear ImGui）。
- 简单方块类型：木头、树叶、石头、沙子、水（水面半透明单独 mesh）。
- 里程碑：有"可以挖挖挖、捡东西、放火把"的原型生存体验。

### V0.5 超大世界优化（预计 4~8 周）

- LOD（2×/4× 合并网格）+ Impostor 远景。
- 视锥体裁剪 + 基础 occlusion culling。
- 渲染距离拉到 **16~24 区块**，目标稳定 60 FPS。

- 简单怪物 AI（僵尸、猪，Jolt 刚体 + 自研 AABB 查询）。
- AO（环境光遮蔽）烘焙到顶点色。
- 里程碑：已经是一个**可玩的 MC-like 游戏**。

### V1.0 正式版（后续持续）

- 多人联机（GameNetworkingSockets，客户端-服务器模型）。

## 9. 开发环境与工作流

### 9.1 推荐环境组合

| 平台 | 组合 |
| --- | --- |
| Windows（主力开发） | Visual Studio 2022 + CMake（≥ 3.21）+ vcpkg（manifest 模式）+ Ninja + ccache |
| Linux（CI/跨平台验证） | Clang/LLVM 16+ + CMake + Ninja + ccache + ASAN/UBSAN 常启；**TSan 单独一套配置**（与 ASAN 互斥，不可同时开启） |
| macOS（可选） | Xcode + Clang + CMake + Ninja；**SDL3_gpu 在 macOS 走 Metal 原生后端，无需 MoltenVK**；若改用备选手写 OpenGL 方案，注意 macOS OpenGL 最高仅 4.1 |

**首次环境初始化清单（按顺序执行）：**

1. **Visual Studio 2022** —— 勾选"使用 C++ 的桌面开发"工作负载（含 MSVC v143 与 Windows SDK）。
2. **CMake ≥ 3.21** 与 **Ninja** —— 随 VS 安装即可，或使用官方安装包。
3. **vcpkg** —— `git clone https://github.com/microsoft/vcpkg`，运行 `bootstrap-vcpkg.bat`，并设置环境变量 `VCPKG_ROOT`。
4. **锁定依赖基线（必做）** —— 在仓库根执行 `vcpkg x-update-baseline --add-initial-baseline`，把生成的 `builtin-baseline` 提交进 `vcpkg.json`；否则各开发机与 CI 的依赖版本会漂移。
5. **Shader 工具链** —— 安装 Vulkan SDK（含 `glslc`）或 SDL 官方 `SDL_shadercross`；本项目 Shader 在**构建期**编译为 SPIR-V。
6. **ccache / sccache**（可选）—— 加速重复编译。
7. **Git + Git LFS** —— 初始化仓库并启用 LFS（PNG / FBX / 音效走 LFS）。
8. **调试工具** —— RenderDoc（截帧分析）、Tracy（性能）。
9. **环境核验** —— `cmake --preset debug` 与 `ctest --preset debug` 均成功，即视为环境就绪。

> **当前开发机核查记录（2026-09-25）**：`cmake / ninja / glslc / dxc / vcpkg / MSVC(cl) / clang-cl / git` **均未安装**，仅 Python 可用。**环境尚未就绪，上述 1~4 项为开工前置条件。**

### 9.3 版本控制与质量保障

- **Git + `.gitignore`**：忽略 `build/`、`out/`、二进制产物、用户 IDE 配置；
- **Git LFS**：大资源（PNG 纹理、FBX 模型、音效）走 LFS；
- **CI（GitHub Actions / 自建）**：每次 PR 在 Windows + Linux 下跑 Debug (ASAN) + Release 构建，**并执行全部单元测试（CTest）**，确保不破编译、不破测试；**TSan 单独一套 Linux 配置**（与 ASAN 互斥）；
- **单元测试（GoogleTest + CTest）**：以下四类**必须有**测试——① 生成确定性（同种子同输出）；② Section/Palette 编解码往返；③ 存档序列化往返 + **版本迁移**（旧档能被新版本正确读出）；④ 光照 BFS 跨界与贪婪合并边界；
- **代码格式化**：`clang-format`（基于 LLVM 风格微调，4 空格、列宽 120），提交前自动格式化；
- **静态分析**：Clang-Tidy 静态检查在 CI 开启，至少启用 bugprone-*、performance-*、modernize-*；
- **Commit 规范**：`[voxel]`、`[render]`、`[engine]`、`[build]` 等前缀区分模块，方便回溯。

## 10. 风险与应对

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 范围蔓延 | 想做的功能太多，长期无法交付 | 严格按路线图，每阶段只聚焦一个可运行目标；V0.5 之前不加多人/光影/模组 |
| 内存/性能瓶颈 | 视距拉高后面数/内存/帧率崩溃 | V0.1 就按 section+palette 设计存储；V0.2 做 Greedy；V0.3 多线程；Profiling 用 Tracy 数据说话，不猜 |
| 架构返工 | 早期数据结构设计不当，后期扩展困难（典型：把方块做 Entity、光照不增量、没有 RHI） | V0.1 就按最终架构搭骨架（section、RHI 接口、Job System）；宁可 V0.1 多花一周想清楚，也不要 V0.4 重写 |
| 单人开发周期长 | 引擎 + 游戏双重工作量巨大 | 大量复用成熟三方库（SDL3/Jolt/EnTT/FastNoiseLite/stb），不重复造轮子；V0.x 不写脚本/编辑器/网络 |
| 跨平台复杂度 | 不同平台 API/编译器差异 | 平台抽象层隔离；V0.x 只保 Windows 跑通，Linux/macOS 等 V0.5 后再做 |
| 多线程 bug | 区块后台生成导致数据竞争、死锁、悬挂指针 | 双缓冲 + 原子指针交换；不要跨线程直接改同一 Chunk；**Windows（MSVC）用 ASAN，Linux/Clang 额外启用 TSan**（MSVC 不支持 TSan，且 ASAN 与 TSan 互斥，须拆成两套 CI 配置分别运行） |
| 光照/网格性能热点 | 火把放置/爆炸触发大范围网格重建 | 光照独立顶点通道（V0.4 之后）；脏区域标记限制到 section 粒度，不整 chunk 重建 |
| 世界坐标精度 | 玩家走远后抖动/穿模 | 世界坐标双精度 + Camera-Relative 渲染；早做，晚改要全引擎改类型 |

## 结语

本方案的核心思路是：**用 C++ 打牢引擎底层，用分层架构隔离通用能力与体素专有逻辑，用分阶段迭代控制风险**。C++ 的性能完全足以支撑渲染距离 32 区块以上的流畅大世界，甚至可以比原版《我的世界》优化得更好——因为你完全掌控所有底层逻辑，没有通用引擎的额外开销。

几个贯穿全局的关键决策再强调一次：

1. **Section + Palette 压缩**，否则撑不住 24 区块视距；
2. **Greedy Meshing 提前到 V0.2**，避免后期重写顶点格式；
3. **分块确定性生成 + 网格抖动**，保证区块只看自身即可重建；
4. **体素碰撞靠子步进 + 自动上台阶，不要缩小碰撞盒**；
5. **多线程 Job System + 双缓冲**，主线程永远不阻塞；
6. **自写二进制 + zstd 序列化**，格式可控、零模板膨胀；
7. **GameNetworkingSockets 做网络**，自带加密与 NAT 穿透。

从 V0.1 的第一个 Section 开始，一步步走到属于你自己的超大世界。
