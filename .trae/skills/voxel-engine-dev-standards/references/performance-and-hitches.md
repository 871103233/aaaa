# 卡顿消除与帧时间预算（防 hitch 的业界标准）

> **性质**：本技能的方法规范之一（挂载点见主文件第四节「卡顿消除」与「任务路由」）。
> **适用**：任何**新增每帧工作 / 新增长任务 / 性能优化 / 卡顿（hitch）定位**的改动，**本文件全部适用**。
> **权威边界**：预算**数字**以 [ADR 0008](../../../docs/adr/0008-sizes-precision-budget.md) 与主文件第四节为准；
> 线程角色与任务图的落地细节见 `concurrency.md`；加载 / 长任务的形态见主文件「不冻结画面」。
> 本文件只写**分类判据、业界手段参照、观测义务与自查清单**。

## 0. 先把"卡"分成三类（判据不同，手段也不同）

| 类别 | 玩家感受 | 可判定判据 | 主要手段 |
| --- | --- | --- | --- |
| **尖峰型（hitch）** | 偶发"顿一下"，其余时间流畅 | 单帧 **> 2× 帧预算**（60 Hz 下 > 33 ms） | §1.1 任务化 + 帧预算队列 |
| **持续型（掉帧）** | 帧时间**随视角 / 位置**变化，"看某些方向发涩" | P95 / P99 帧时间 **> 1.5× 均值** | §1.3 提交侧可控 + §1.2 流式 |
| **加载型（冻结）** | 画面**停止更新**（> 100 ms） | 存在 **> 100 ms** 的"无出帧窗口" | 主文件「不冻结画面」（**无条件禁止**） |

**总判据（本项目）**：稳态下 **P99 帧时间 ≤ 2× 帧预算**，且**不存在 > 50 ms 的单帧**；每秒 hitch 计数 = 0。

> 只看**平均**帧时间必然漏掉 hitch —— hitch 是**尾部**问题，必须看 P95 / P99 与单帧分布。

## 1. 四层手段（业界标准，逐条给具体参照）

### 1.1 不让重活落在渲染帧里（任务化 + 帧预算队列）

- **业界参照**：UE5 的 **Task Graph** 与 "time-sliced" 工作（一次大活切成若干 tick 的预算单元）；
  Unity 的 **Job System + Burst**；Naughty Dog / Insomniac 的 GDC "hitch-free" 系列
  （先把 hitch 定义为"超过一帧预算的可感知停顿"，再据此做预算表）。
- **规则**：任何**单次 > 3 ms** 的操作，必须 ① **按帧切分**（预算队列），或 ② **下沉 worker**；
  主线程只做**确定性收口**与 **GPU 上传**。
- 本项目落点：`concurrency.md`（enkits / 线程角色）、主文件「不冻结画面」。

### 1.2 流式与增量（让每帧的活有上界）

- **业界参照**：Minecraft 类区块流式（按距离 / 视线**提前预取**）；Horizon 的 streaming budget
  （流式工作按帧配额分配）；id Tech 的 texture / page residency（缺页才加载，且**在可见之前**完成）。
- **规则**：
  1. 预取必须**提前 N 帧**完成 —— "到眼前才开始做"必然表现为 hitch；
  2. 只重建**脏块**，禁止整世界 / 整块重建；
  3. **LOD 切换在远处完成**（近处切 LOD 时，构建成本与几何突变都会被抓到）。

### 1.3 提交侧可控（成本不随视线波动）

- **业界参照**：视锥剔除 + **遮挡剔除**（UE 的 HZB occlusion、GPU 端 Hi-Z）；**GPU-driven rendering**
  （GPU culling + indirect draw）；**每帧一次 uniform / storage 上传**而不是逐物体 push；
  **PSO 预建缓存**（UE 的 PSO cache / `FShaderPipelineCache`）与 shader 预热。
- **规则**：
  1. 提交的网格数必须由**剔除结果**决定，而不是"全部网格"；
  2. **逐物体 uniform 推送**必须与"每帧上传次数"**解耦**（合并成一次 storage buffer）；
     推送次数随**世界总量**线性增长**视为缺陷**；
  3. **资源与管线创建不得发生在渲染热路径**：PSO / 纹理 / 缓冲只允许在加载期或**分帧创建队列**里出现
     （否则表现为"首次看到某材质 / 某物就卡一下"）；
  4. **例外（判据，T41 起明文）**：若某值**逐物体确实不同**且无法合并（例：每个网格的**世界原点** ⇒ 逐网格偏移），
     允许逐物体推送**小常量**（≤ 64 B 的 push constant / root constant），条件是 ——
     ① 它是**推送**不是**上传**（不创建 / 不拷贝 GPU 缓冲、不同步等 GPU、不建 PSO）；
     ② 次数上界 = **剔除后的可见网格数**（不随世界总量增长）且**有实测**；
     ③ 值相同的连续网格**必须去重**（`VertexOffsetPushState` / `EmissivePushState` 那一套）。
     **真正的违规**是"逐物体**上传**""逐物体**创建资源**"或"次数随**世界总量**增长"；
     能用 storage buffer 一次上传 + 索引表达时仍**优先**那条路（本节第 1 条的业界参照）。

### 1.4 帧节奏（pacing）

- **业界参照**：固定步长 + 渲染插值（**本项目已用**，见红线 11）；present mode 选择
  （vsync / **mailbox** / immediate）；**三重缓冲 + CPU 提前一帧** —— 让"等 GPU / 等交换链"的时间被
  下一帧的 CPU 工作**填掉**，而不是空等。
- **规则**：不得在渲染帧内 `WaitForGPU` 或做同步上传；一切"等待"必须**可观测**（等待时长要进观测数据），
  且不能让帧时间与 GPU 负载无关地抖动。
- SDL_gpu 专项：`SDL_WaitAndAcquireGPUSwapchainTexture` 的等待发生在 `RenderFrame` 内部，
  **必须能被观测区分**（否则会把"在等"误判成"CPU 忙"）。

## 2. 观测义务（先证据、后优化）

**硬规则**：**任何性能结论必须来自数据**。禁止"感觉更快了""应该就是这个原因"。

| 手段 | 内容 | 何时必须用 |
| --- | --- | --- |
| **帧尖峰打点** | 帧时间超阈值时打印「三相 CPU（逻辑 / UI / 渲染提交）+ draw call + 提交网格数 + 是否在等交换链」 | 定位任何 hitch 的**第一步**；也是唯一能区分"CPU 忙 / GPU 忙 / 在空等"的手段 |
| **分位数** | 报 **P50 / P95 / P99**，不只报均值 | 任何性能结论 |
| **Tracy**（V0.2 起） | CPU 帧时间、线程时间线、GPU zone | 性能改动**必须附对比数据** |
| **RenderDoc / PIX** | 截帧看各 pass 耗时与管线状态 | 渲染侧卡顿 |

## 3. 本项目自查清单（每次新增"重活"逐条过）

| 检查项 | 判据 | 违反时的表现 |
| --- | --- | --- |
| 新增的每帧工作是否与**总量**成正比？ | 必须与"可见量"成正比（剔除之后） | 视角一转就掉帧 |
| 每帧是否有**逐物体**的 API 调用（**上传** / 资源创建 / 单独绑定）？ | 上传与资源创建**必须**合并 / 分帧；逐物体**小常量推送**仅限"值确实逐物体不同"，且上界 = 可见网格数 + 去重（见 §1.3 第 4 条） | 提交量随**世界总量**增长 / 每帧多次阻塞上传 |
| 新增操作的最坏**单帧**耗时是多少？ | 必须**实测**且 ≤ 帧预算 | 偶发"顿一下" |
| 是否引入"**首次命中才创建**"的资源（PSO / 纹理 / 缓冲 / 形状）？ | 只允许加载期或分帧创建队列 | 第一次看到某物就卡 |
| 是否在新路径里**同步等 GPU**？ | 禁止（上传除外，且必须可观测） | 帧时间与 GPU 负载耦合 |
| 是否让**提交量 / 采样量随视线方向**变化？ | 变化必须有上界且被测量 | "看某些方向发涩" |
| 长任务是否**按帧切分**或有**进度反馈**？ | 见主文件「不冻结画面」 | 加载 / 破坏时画面冻住 |

## 4. 伪优化与误判（本项目真实反例，禁止重犯）

| 反例 | 为什么没用 |
| --- | --- |
| 提高帧率上限 / 改呈现模式 | 只改变**节奏**，不改变单帧工作量 ⇒ hitch 依然存在（实测：帧率改 360 无改善） |
| 关闭 F1 面板 | 只省 UI 构建（亚毫秒级）⇒ 实测无改善，说明 hitch 不在 UI |
| 只看 CPU 三相 | GPU 侧成本（采样 / 带宽 / 填充率）看不到 ⇒ "看山卡"一度被判到 CPU，实际是 `mesh.frag` 的三平面采样（T35） |
| 只看平均帧时间 | hitch 是**尾部**现象 ⇒ 必须看 P95 / P99 与单帧分布 |
| 凭直觉改代码 | 无证据的优化会引入新缺陷且无法证明有效 ⇒ **先打点，再改** |

## 5. 与其它节的关系（边界，避免两处并存的口径）

- **与「不冻结画面」**（主文件第四节）：那节管**加载 / 长任务的形态**（先给画面、再给结果、进度可见）；
  本节管**分类、通用手段与观测义务**。两者**叠加适用**，不存在替代关系。
- **与「降级必须先问」**（主文件「3A 基线」）：达不到"P99 ≤ 2× 帧预算 / 无 > 50 ms 单帧"时，
  **必须提问并登记**，不得默默接受、也不得只写进 `docs/devlog.md` 就算闭环。
- **与「性能预算」**（主文件第四节）：预算**数字**（≥ 60 FPS / CPU ≤ 150 MB / VRAM ≤ 300 MB）仍以
  ADR 0008 与第四节为准，本节**不另立数字**。
- **与 `concurrency.md`**：§1.1 的落地细节（线程角色、任务图、GPU 上传时序）以那份为准。

## 6. 禁止项速查

- 在渲染帧内同步跑完一个明显超帧预算的任务；
- 用"降低画质 / 提高帧率上限 / 关面板"掩盖 hitch（hitch 未消除即未闭环）；
- 逐物体**上传** / 逐物体**创建资源** / 提交量随**世界总量**增长（逐物体**小常量推送**仅在 §1.3 第 4 条的三条判据下允许）；
- 在渲染热路径里创建 PSO / 纹理 / 缓冲（"首次命中才创建"）；
- 在渲染帧内 `WaitForGPU`；
- **无数据**就下性能结论，或不打点直接改代码。
