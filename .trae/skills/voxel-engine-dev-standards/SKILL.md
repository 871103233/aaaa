# 体素引擎开发规范

本文件是本仓库的**强制施工规则**。选型理由与备选方案对比见方案文档
`docs/tech-plan-v1.3.md`，本技能只保留**可检查的硬约束**。
两者冲突时以方案文档为准，并回来修正本技能。

## 阅读约定（先读这一节）

本文件**全部是规则**。凡标注「禁止 / 禁用 / 不使用 / 暂缓」的条目，都是**不得执行**的动作，**不是待办事项**；
每条禁止都对应一个必须执行的正向做法，**一律以正向做法为准**。
「备选方案」是默认不启用的兜底项，不是并行候选，仅在出现明确切换条件并经确认后采用。

### 会话启动：先读「交接包」

**任何一次新会话**（新开对话、换人接手、上下文被重置）**在动手前必须先读以下 6 份「交接包」**，
按此顺序读，**不得凭对话记忆或印象推断项目状态**：

| # | 文件 | 读它回答什么 |
| --- | --- | --- |
| 1 | 本文件 `SKILL.md` | 规则是什么（红线、分层、DoD、范围控制） |
| 2 | `docs/devlog.md` | 已经做完什么、还剩什么（**看文末最新条目**） |
| 3 | `docs/plans/<当前阶段>.md` | **当前阶段的任务分解、顺序、进度与下一步**（见第六.4 节） |
| 4 | `docs/tech-plan-v1.3.md` | 技术决策与备选方案（选了哪个、为什么） |
| 5 | `docs/file-index.md` | 目录结构与各层职责（什么该放哪里） |
| 6 | `docs/learning-notes.md` | 名词与概念（不懂的先查这里，**不要重复问**） |

- **不要求用户重述历史**：凡已写入上述文件的，一律以文件为准。
- 读完交接包后，再按下方「任务路由」读与当前任务相关的那一份 `references/*.md`。
- **一份都没读就开工 = 违规**；若某份文件缺失或与实际不符，**先报告再继续**，不要默默绕开。

### 需求受理：先判合理性，再按业界标准执行

**接到需求先做三步，再动手。**

**第一步：判定合理性（必须给依据，不许凭感觉）**

| 判定 | 处理方式 |
| --- | --- |
| **合理，且存在"与要求不矛盾的更优做法"** | **直接按更优做法实现**，不必回头问；在回复中**明确对照**"你要的效果 / 我们的实现方式 / 依据"，并写进 `docs/devlog.md` 的「为什么」 |
| **与要求矛盾**（会改变用户要的效果） | **不动代码**：列出冲突点、候选做法与各自代价，向用户提问，等答复 |
| **技术上不可行 / 撞红线** | **不动代码**：指出冲突的 ADR、红线或预算条目，给出可行替代，再问 |

**第二步：查业界标准做法（默认动作，不是可选项）**

- 任何需求**先问"业界同类产品怎么做的"**，再决定实现方式；**不要等用户点名具体技术手段**。
- 判定链：① 业界标准做法是什么（能给出 2~3 个同类产品的做法作为依据）→ ② 在本项目约束下能不能用
  （红线 / 分层 / 预算 / 确定性）→ ③ 用不了时给最接近的替代并说明差异。
- **反例（本项目真实踩过）**：用户反馈"鼠标转向有问题，建议锁定鼠标"。**锁定光标（相对鼠标模式）本就是第三人称 3D 游戏的标准做法**，
  应当在**实现第三人称相机的当次**就做，而不是等用户提出——**把业界默认项当成"用户额外需求"是本条要禁止的行为**。

**第三步：与「第五节 范围控制」的边界（防止借"业界标准"之名扩张）**

- 只有**"不做会导致体验明显残缺、或日后必须返工"**的才算"业界默认项"，**直接做**
  （例：光标锁定、俯仰限位、失焦处理、相机不穿墙、窗口可缩放）。
- 纯增强与锦上添花（粒子、后处理、天气……）**仍走第五节范围控制**，不得以"业界也这么做"为由引入。

**判定示例（本项目真实案例，照此口径判断）**

| 用户要求 | 判定 | 处理 |
| --- | --- | --- |
| "上下各看**满 90°**" | 合理，但**正好 90° 会让 `lookAt` 退化出 NaN**（与 B2 蓝屏同源） | 属"**不矛盾的更合理做法**" ⇒ **直接**按 **±89°** 实现（留 1° 余量），并在回复与 devlog 说明 |
| "鼠标转向有问题"（未提锁定） | 业界标准 = **相对鼠标模式（锁定光标）** | 通过第二步 ⇒ **主动实现**，不等用户点名 |
| 假设要求"改成第一人称" | 与既定"第三人称跟随"**矛盾** | **不动代码**，先提问（影响相机、角色表现与整体手感） |

**记录义务**：凡**按更合理做法执行**而非字面执行之处，必须让用户一眼看出**"你要的效果 → 我们的实现方式 → 依据"**，
并写入 devlog；**不得**让用户以为需求被悄悄改掉了。

### 任务下发：每次任务都必须先有「进度 + 规划」

**任何一次任务下发**（新需求、继续开发、修 bug、纯文档改动）在动手前，
必须先把本次任务写进 `docs/plans/<当前阶段>.md`，再开始施工；**没有计划条目的动手视为违规**。

计划条目至少写四件事：

| 项 | 要求 |
| --- | --- |
| **范围** | 本次做什么、**明确不做什么**（防范围蔓延） |
| **顺序** | 拆成可独立验证的小步，标出先后与依赖 |
| **落点** | 涉及的目录 / 模块入口 / 文档（便于按 `file-index.md` 核对） |
| **验收** | 可观察的判据（命令 + 预期结果）；阶段级验收**引用**方案 §8，不复制 |

- 计划是**活文档**：每完成一步即勾选该步，并更新「当前进度」与「下一步」，与代码**同一次提交**。
- 计划**不写技术结论**：选型、理由、备选一律指向权威层（方案文档 / ADR），计划里只引用、不改写。
- 每次开工**先读**当前阶段计划，**不要求用户重述进度**；计划与实际不符时，**先报告再改计划**。
- **必须能只读这一份文件就开工**：接手者（人或大模型）不得被迫重读全部 devlog 才能知道下一步做什么。

### 会话边界：按任务阶段开新会话

- **同一任务未闭环** → 留在当前会话，不切换。
- **任务已闭环、进入新阶段**（例如从 PoC 转入 V0.1 开发）→ **开新会话**，开场即按上面的交接包清单启动。
- **切换前必须落盘**：任何未决项、口头约定、待确认结论，都要写进 `docs/devlog.md` 的「下一步 / 遗留」、
  当前阶段计划的「阻塞 / 未决」或对应文档。
  **只存在于对话里的信息，换会话即丢失，等同于没记录。**
- **阶段切换时必须新建计划**：上一阶段计划冻结不动，新阶段新建 `docs/plans/<新阶段>.md`。

## 技术栈：单一事实来源与口径统一

本节是**防止"同一条技术结论在不同文档里被写成不同样子"的机制**。上次的教训是：
"Shader 只编 SPIR-V"这条结论同时散落在技能、方案、ADR 三处，改了一处、漏了三处，
于是后来按旧结论施工直接断言失败。规则与红线表同等强制。

### 1. 三层职责（谁写什么）

| 层 | 位置 | 只允许写 |
| --- | --- | --- |
| **权威层** | `docs/tech-plan-v1.3.md` 各章、`docs/adr/*.md` | 决策本身、选型理由、备选方案、**切换条件**。**只有这里能写"为什么"** |
| **索引层** | 本节下方的「唯一口径表」 | "是什么"——每格**只能有一个值**；不写理由、不写备选、不写版本号，细节一律指向权威层 |
| **执行层** | 本技能 `references/*.md` | "怎么落地"的硬约束与检查项；不重复决策与理由 |

**核心规则**：任何技术结论**只在权威层展开一次**；索引层与执行层只能**引用**，
不得改写、不得补细节、不得留第二个候选。

### 2. 唯一口径表（照此执行，除此别无第二写法）

> **口径现状（2026-09-25 更新）**：世界表示已由 **ADR 0004** 改为**分层混合**，且新版方案

### 3. 名称陷阱：vcpkg 端口名 ≠ 业界通称

写进构建配置时**一律用 vcpkg 端口名**；文档里首次出现用"通称（端口名）"形式：

| 通称 | 实际端口名 |
| --- | --- |
| enkiTS | `enkits`（**无连字符，也不是 `enki-ts`**） |
| EnTT | `entt` |
| Taskflow（备选） | `taskflow` |
| SDL_shadercross | `sdl3-shadercross` |
| GoogleTest | `gtest` |
| GLM | `glm` |
| zstd | `zstd` |
| Jolt Physics | `joltphysics`（**不是 `jolt`**；实测 `5.6.0#1`） |
| toml++ | `tomlplusplus`（实测 `3.4.0#1`；见 ADR 0005） |
| Dear ImGui | `imgui`（SDL3_gpu 需 `imgui[sdl3-binding,sdlgpu3-binding]`，实测 `1.92.9`） |
| stb_image | `stb`（实测 `2024-07-29#1`） |
| Tracy | `tracy`（实测 `0.14.1`；V0.2 起引入） |

### 4. 选型变更：四步流程（缺一步即未完成）

1. **写 ADR**：背景 / 决策 / 备选对比 / 后果 / 何时重新审视。**未采纳方案必须留档并写明切换条件**。
2. **改权威层原文**：方案文档对应章节 + §5 清单。
3. **按下方「同步清单」逐处改口径**：用第 2 节表里的措辞，**逐字照抄**，不改写、不节选。
4. **追加 `docs/devlog.md`**，并跑一次第 6 节的「口径漂移自查」。

### 6. 口径漂移自查（改完跑一次）

用 Grep 搜下列关键词，逐条确认不存在第二种写法（每行都可直接作为 `pattern` 使用）：

- `enkiTS|Taskflow|enkits` —— 没有"A 或 B"、没有把旧通称当端口名用
- `SPIR-V` —— 没有写成单一格式、没有仍要求安装 Vulkan SDK
- `C\+\+20` —— 没有与"C++17 唯一标准"冲突的表述
- `自研稀疏集|自研 ECS` —— 没有与"EnTT 起步"冲突的表述
- `V 或 Vendored|或 \*\*|/ \*\*` —— 不存在并列候选
- `96 KB|16×16×384|Section 16³|贪婪合并|swept AABB|quadSize` —— 没有把已由 ADR 0004 取代的旧世界表示口径当成**现行规则**（合法命中仅限迁移期声明、ADR 0004、devlog 与方案文档的历史条目）

**预期的合法命中**：只有本表自身，以及"备选方案说明"「端口名对照」与 devlog / 方案文档的**历史修订记录**。
除这三类之外的任何命中，都视为口径漂移，必须当场改掉。

## 二、分层与依赖方向

`platform → engine core → world → game`

- 依赖只能向上：下层不 include 上层头文件（`engine/` 不引用 `world/`、`game/`）。
- `engine/` 内只放通用类型，不放世界 / 游戏专有类型（`TerrainTile`、`DigVolume`、`Biome` 等）。
- `world/` 只经引擎核心层与平台抽象层访问硬件，不直接调用平台 API。
- **需要预编译**的第三方库只在平台层或引擎核心的薄封装中直接引用。
- **纯 header-only 的 vendored 库**（`third_party/`，如 FastNoiseLite、toml++）允许在 `world/` 的 `.cpp` 内直接使用，
  但**不得出现在任何公共头文件中**（须以 pimpl 或自有类型隔离）；同一库一旦扩散到多个模块、或泄漏进公共头，
  必须抽到 `engine/` 薄封装后再用。`third_party/` 目录本身被门禁脚本排除。

## 三、编码约定

- 标准：**C++17**。只使用 C++17 及以下的语言与库设施，**不使用 C++20 特性（Modules、`std::jthread` 等）**。
- 命名：类型 / 枚举 `PascalCase`；函数与方法 `PascalCase`；局部变量与参数 `camelCase`；
  成员 `m_camelCase`；编译期常量 `kPascalCase`；宏 `UPPER_SNAKE`；文件 `snake_case.h` / `snake_case.cpp`。
- 头文件：一律 `#pragma once`；头文件内不使用 `using namespace`；优先前置声明。
- 所有权：`unique_ptr` / 句柄 / 资源池；不用裸 owning 指针与散落的 `new/delete`。
- 错误处理：热路径用返回值传递错误，不做运行时分配、不抛异常；启动期可用异常。
- 不使用 RTTI（`dynamic_cast` / `typeid`）；需要区分类型时用 tag 或 variant。
- 常量正确性：能 `const` 一律 `const`。
- 日志走统一日志宏 / 接口，不散落 `std::cout` / `printf`。
- 注释：公共接口用 Doxygen 说明意图与前置条件；实现内不复述代码。
- Shader：GLSL 源 + 自写 include 预处理，经 `glslc` → **SDL_shadercross** **两段式**离线编译，
  **同时产出 SPIR-V 与 DXIL**（格式由渲染后端决定，只产一种会在另一种后端上断言失败）；
  运行时按 `SDL_GetGPUShaderFormats()` 选择加载哪一种。见 ADR 0002。

## 四、性能预算（超出即视为缺陷）

**权威口径见 [ADR 0008](../../docs/adr/0008-sizes-precision-budget.md)（尺寸 / 精度 / 预算）与本技能「唯一口径表」的"预算与精度"一行；本节只列必须遵守的形态。**

- **尺寸与精度**：地表 tile **64×64 列**、高度 `int16`（1/16 格）；可挖体积块 **32³ 体素**（33³ 采样）、密度 `int8`；世界垂直范围 0~512 格。
- **V0.1 预算**（小场景，基线机 1080p）：**≥ 60 FPS**；CPU 常驻 **≤ 150 MB**；VRAM 常驻 **≤ 300 MB**。
- **Draw Call 与长视距内存：只记录、不验收** —— 二者取决于尚未收敛的地表 LOD 方案（待收敛项 4）；收敛前不得给数字，也不得引用旧数字。
- **已作废、不得再作验收依据的旧数字**：`16×16×384` / 光照 `96 KB` / `≤700 draw call` / `3×3×3 方块碰撞查询` / 2401 区块内存估算。
- 主线程帧内只做渲染、输入、相机与碰撞查询；生成、网格化、文件 IO、等待 GPU 都放到后台或上传阶段。
- 任何性能相关改动必须附 **Tracy** 对比数据（V0.2 起），不接受"感觉更快了"；比对须在 `tech-plan-v2.0.md` §7 的**固定基准场景**下进行。

写法要求：

- 写**依据与结论**；`git log` 已有的事实不必复制。
- 「验证」一栏必须可复现：给命令与真实输出，取代"应该没问题"。
- **失败与弯路同样记录**：只记成功会丢掉一半信息。
- 每条聚焦一个主题，避免待办清单式的流水账。

### 六.3 学习笔记（`docs/learning-notes.md`）

用途：把**解释过的名词、答过的技术疑问、引入的新技术、安装的工具**沉淀成可检索的笔记，
避免知识只活在对话里、同一个问题反复问。

必须记录的触发条件：

| 触发 | 例子 |
| --- | --- |
| 用户问一个**名词解释** | "PoC 是什么" |
| 用户问一个**与当前项目相关的技术疑问** | "为什么 D3D12 要 DXIL 而不是 SPIR-V" |
| **引入新技术 / 新库 / 新工具** | 安装 `shaderc`、引入 zstd |
| 出现**改变既有认知的发现** | "原以为只编 SPIR-V 就够" |

组织方式：**固定分区，就近归入既有类别**；确实无归属才新增分区，并在文件顶部目录登记。

| 分区 | 内容 |
| --- | --- |
| A 技术选型名词 | 渲染 / 生成 / 存储 / 并发 / 物理等选型术语 |
| B 开发流程与工程用语 | PoC、CI、ADR、门禁、DoD、Sanitizer 等 |
| C 已安装的工具 | 名称、版本、位置、**为什么需要它** |
| D 本项目专属概念 | 分层混合世界、双格式 Shader 管线等 |
| E 疑难问答 | 一次性的具体问题与答案（问题 + 结论 + 原因） |

每条格式：

````markdown
### <名词>

- 一句话定义：
- 在本项目里是什么 / 为什么需要：
- 易错点或关键取舍：
- 相关：<指向其它笔记、ADR 或方案文档章节>
````

分工边界（五者不重复）：

- **学习笔记**写「概念本身」——这个名词是什么意思。
- **开发记录**写「过程」——我们做了什么、为什么、验证结果。
- **方案文档 / ADR** 写「决策」——选了哪个、备选是什么、对比与切换条件。
- **阶段计划**写「计划与进度」——接下来做什么、按什么顺序、做到什么程度算完、现在到哪了。
- **内容基线文档**写「有什么」——世界与项目里**已存在与待存在的内容、设定与状态**；
  它不写理由（去 ADR）、不写进度（去阶段计划）、不写名词解释（去学习笔记）。
- **引擎能力**（六.6）写「引擎能做什么」，**游戏设计**（六.7）写「我们要做哪款游戏」——两者**必须分开**；
  同一件事横跨两边时：**能力写在六.6、需求写在六.7**，互相链接，**不重复叙述**。

写入时机：**当场写**，不积压到"以后再整理"。

### 六.4 阶段计划（`docs/plans/<阶段>.md`）

用途：回答**"这个阶段要做哪些任务、按什么顺序、做到什么算完、现在到哪了"**，
使接手者（人或大模型）**只读这一份文件即可开工**，不必重读全部 devlog 反推进度。

命名与粒度：**每阶段一份**，`docs/plans/v0.1.md`、`docs/plans/v0.2.md`……
**阶段闭环后冻结不回改**，进入新阶段时新建文件。

必须包含四部分：

```markdown
# <阶段> 开发计划

- 依据：`docs/tech-plan-v1.3.md` §8「<阶段>」的阶段目标与验收标准（**引用，不复制**）
- 施工细则：`references/<与本阶段对应的引用>.md`
- 状态：未开始 / 进行中 / 已完成（冻结）

## 1. 前置条件
| # | 前置项 | 状态 | 说明 |

## 2. 任务分解
| # | 任务 | 落点（目录 / 模块入口） | 验收判据 | 状态 |

（状态取值：未开始 / 进行中 / 已完成 / 阻塞）

## 3. 当前进度
- 已完成：
- 进行中：
- **下一步**：（必须是一句话就能开工的可执行动作）
- 阻塞 / 未决：（未决项须同时登记到本技能「待收敛项」表，并写明收敛时限）

## 4. 阶段验收对照
| 验收维度 | 状态 | 依据 |

（维度名取自方案 §8 验收表的维度列；判据列只写"方案 §8"，不复制其内容）
```

维护规则：

- 每完成一步：勾选该步 → 更新「当前进度」 → **与代码同一次提交内完成**。
- 任务下发时先补计划条目（范围 / 顺序 / 落点 / 验收），**再动手**。
- 计划**只引用**技术结论（指向方案文档 / ADR），**不写理由、不写备选、不留第二个候选**。
- 计划与实际不符时：**先报告再改计划**，并在 `docs/devlog.md` 说明变更原因。
- 「下一步」必须可执行、可验收；写"继续优化""完善细节"这类无法判定的措辞视为未填。

### 六.5 内容基线文档总则（适用于六.6 / 六.7 / 六.8 / 六.9 / 六.10）

**五份内容基线文档**指：引擎能力与产出范围、游戏设计、NPC 行为逻辑、世界观设定、界面与交互清单。
它们回答的是**"这个世界、这个项目里有什么"**，而不是"我们做了什么"。

**分层硬规则：引擎能力与游戏设计必须分开写。**
`engine-capabilities.md` 只回答"引擎能做什么"，**不得出现具体游戏的玩法、主角、题材或阶段范围**；
`game-design.md` 只回答"我们要做哪款游戏、要求什么"，**不得复述引擎实现细节**（只引用能力名与落点）。
需求若依赖引擎**尚缺**的能力，**两边各占一行**并互相链接。

**共同维护规则（违反即返工）：**

1. **文档缺失时先建立再动手**：涉及某类内容（引擎能力 / 游戏需求 / NPC 行为 / 世界设定）而对应文档不存在时，
   **先按本节模板建立文件**，再写代码。
2. **未开发的内容先占位**：还没有实现或还没定的部分，**必须在文档里占一行并标 `未开始` / `待补`**，
   写清"待谁补、依据什么补"。**留白与"以后再说"都算未完成。**
3. **先登记后动手**：新增任何可生成内容、行为约定或设定，先在文档登记（状态 `未开始` / `待补`），
   实现完成后回填状态与落点。
4. **改动即同步**：一次改动只要**涉及**这三份文档覆盖的内容，就**必须同一次提交内**更新对应文件，
   与"改了代码顺手补文档"不同——这里是**内容本身变了才改**，无关改动不得乱改。
5. **单一结论，不写"A 或 B"**：涉及**技术选型**（决策模型、寻路表示等）的项，候选与理由写在 **ADR**，
   并登记到第 7 节「待收敛项」表、写明时限；内容文档里只写**已定的单一结论**或 `待补`。
6. **不得虚构**：AI **不得**编造世界观、地名、种族、历史或 NPC 设定；只能搭结构、整理已有输入、列出待确认问题。
7. **落地才算生效**：影响生成规则或玩法参数的设定，必须同时进入 `assets/config/` 或阶段计划，
   只写在内容文档里视为**未生效**。
8. **引用不复制**：与 ADR、方案文档、阶段计划重复的内容只引用（给相对链接），不重写一份。

### 六.6 引擎能力与产出范围（`docs/engine-capabilities.md`）

用途：回答**"引擎本身能做什么"**——平台与运行时、渲染、世界生成与表示、物理与角色、
实体 / 任务 / 数据、调试与工程质量，**各自的实现状态**。**与具体游戏无关**。

必须包含：**状态图例**（已实现 / 部分实现 / **已引入未使用** / 未开始）、
**按能力分类的清单表**（每行：能力 / 状态 / 落点模块 / 依据的 ADR）、
**"引擎不包含什么"的分层边界表**（玩法、设定、NPC 一律指向对应游戏层文档）、**登记规则**。

必须更新的触发条件：

| 触发 | 说明 |
| --- | --- |
| 新增 / 修改 / 移除**任何引擎能力** | 新的渲染路径、新的碰撞体类型、新加载器、新的世界表示特性等 |
| 能力**状态变化** | `未开始` → `部分实现` → `已实现`；或从"依赖已装"变成"真的用上了"（`已引入未使用` → `已实现`） |
| **能力落点或依据变化** | 换了模块、换了 ADR |

### 六.7 游戏设计（`docs/game-design.md`）

用途：回答**"我们要做哪款游戏、要求什么"**——题材定位、世界生成要求（每次随机 / **必备元素可定义** /
**预设固定地图**）、玩家能力（跑 / 飞 / 收集 / 破坏地形）、主角与当前阶段范围。

必须包含：**游戏定位表**（题材 / 视角 / 尺度等，未定的写 `待补`）、
**当前阶段需求表**（每行须可判定：需求 / 状态 / 实现方式与落点）、
**明确不在当前阶段的范围**（防蔓延）、**主角占位表**、**与其它文档的分工表**、**登记规则**、
**待项目所有者确认的问题**。

必须更新的触发条件：

| 触发 | 说明 |
| --- | --- |
| 新增 / 修改 / 移除**游戏需求或玩法规则** | 新的世界生成要求、新的玩家能力、新的收集 / 交互规则 |
| 需求**状态变化** | `未开始` → `部分实现` → `已实现` |
| **范围变化** | 某项从"当前阶段"移出或移入（须同时改阶段计划） |

**与六.6 的边界**：本文件写"要什么"，**不写引擎怎么实现**；需求依赖的引擎能力若尚缺，在六.6 占一行并互相链接。

### 六.8 NPC 行为逻辑（`docs/npc-behavior.md`）

用途：回答**"NPC 有哪些、怎么想、怎么动、怎么交互"**。技术约束（ECS、固定步长、确定性、不阻塞主线程、
寻路查询对象）写在文件里；**决策模型与导航表示的选型写在 ADR**，本文件只引用。

必须包含：**与其它文档的分工表**、**技术约束**、**待填内容清单**（种类与层级 / 感知与记忆 /
决策方式 / 移动与寻路 / 日程与生活 / 交互与战斗 / 生成与生命周期）。

必须更新的触发条件：任何涉及 **NPC、生物、寻路、日程、群体行为、对话与战斗**的改动。

### 六.9 世界观设定（`docs/world-setting.md`）

用途：回答**"这个世界是什么"**——题材与基调、地理与生态、种族与文明、历史、命名规范，
以及**哪些设定会影响生成规则**。

**最重要的一条**：**内容必须来自项目所有者；AI 不得代拟。** AI 只做搭结构、整理已有输入、
把缺失项标 `待补` 并列出待确认问题。

必须更新的触发条件：任何设定条目被确定、修改，或某项设定开始影响生成 / 玩法参数时。

### 六.10 界面与交互清单（`docs/ui-inventory.md`）

用途：回答**"游戏里有哪些界面、怎么打开、上面每个控件承诺做什么"**。

必须包含：**两条最高规则**（见下）、**状态图例**、
**界面清单**（每个界面写清五件事：位置 / 打开方式 / 关闭方式 / 与鼠标捕获的关系 / 依赖）、
**控件清单**（每个控件写清四件事：类型 / **名义承诺（点了会发生什么）** / 状态 / 当前限制）、
**设置项与持久化**（取值范围、默认值、**落盘路径**、生效方式）、**登记规则**。

必须更新的触发条件：

| 触发 | 说明 |
| --- | --- |
| 新增 / 修改 / 删除**界面或控件** | 新面板、新按钮、新滑块、打开方式变化 |
| 控件的**行为或状态变化** | `未开始` / `部分实现` → `已实现`；或某控件的"当前限制"消失 |
| **设置的落盘位置或字段变化** | 路径、文件名、字段增删 |

**两条硬规则（违反即返工）**：

1. **控件标签即行为契约**：写着"退出游戏"就必须**真的退出进程**；写着"全屏"就必须**真的切换显示模式**；
   写着"音量"就必须**真的改变音量值并接到音频增益路径**。**禁止放上"点了没反应"的无效控件。**
2. **依赖缺失时显式标注，而不是做成假的**：若控件的名义承诺依赖**尚未实现**的子系统（例：音量依赖音源与混音），
   处理方式是**接通生效路径 + 在「当前限制」列写明"当前听不到效果 + 缺什么才能听到"**，并在回复中告知项目所有者；
   **不得**默默放一个无效控件，**也不得**为此顺手实现整个子系统（那属于范围之外，须先登记需求）。
3. **界面与输入的关系必须写清**：面板打开时是否释放鼠标捕获、是否抑制游戏内输入（挖 / 堆 / 移动 / 视角）。

## 七、品质门槛：可见产出不得以"能跑"结案

**核心规则：功能可用 ≠ 完成。** 凡是**用户看得见、点得到、能感受到**的产出（界面、视觉效果、手感、文案），
除"功能正确"外还必须过**品质门槛**；**未过门槛不得标记为已完成**。

### 7.1 适用范围

新增或修改任何**用户可见 / 可交互**的产出：界面与控件、角色与相机手感、视觉风格（配色 / 字体 / 间距）、
加载与错误提示、音效等。纯内部重构、纯数据管线不适用本节（但仍受"能跑且可测"约束）。

### 7.2 界面品质清单（UI 必过）

- **可读**：字体可加载、**不得出现缺字（`?`）**、字号舒适、对比度足够、**不依赖"假设运行环境装了某字体"**
- **一致**：配色 / 圆角 / 间距 / 边框来自**单一样式入口**，不得散落临时样式
- **整齐**：控件按功能**分区**、标签与数值**对齐**、间距统一、面板尺寸与位置合理、**不裸放控件**
- **名义契约**：每个控件都实现其标签承诺（见第六节六.10），**无无效控件**
- **状态可见**：当前值可见（如音量显示数值）、禁用态明确（如全屏时分辨率置灰）
- **边界完整**：窗口缩放、极值（0 / 最大）、非法输入、焦点丢失均有确定行为

### 7.3 提前做，不做事后补救

品质要求在**第一次交付**时就满足——**不得**先交"能跑但很丑"、再由用户指出来。这是「需求受理」第二步
（业界标准即默认动作）在**质量维度**的延伸。

### 7.4 如何证明

- **能自动化的必须自动化**：不崩溃、字体解析与回退、标签回退全 ASCII、布局关键断言、设置读写与钳制
- **不能自动化的必须显式标注**：观感、手感、配色舒适度一律标注"**待人工目视验收**"，
  并在回复中写清**"看哪里、期望看到什么"**
- **未过门槛的部分必须列为待办**并写明差距，**不得**用"已完成"掩盖

### 7.5 反面示例（本项目真实案例）

UI 面板首版**功能全部可用**（全屏 / 分辨率 / 音量 / 退出都真的生效），但**字体缺字成 `?`、无主题、控件裸放** ⇒
用户第一眼判定"很丑、不像完成"。按本节：该次交付**应当标注"功能可用、品质未达标"并列出待办**，而不是当作完成；
**事后再补字体与主题的成本，高于一开始就做对。**

- [ ] 命名与头文件约定符合第三节
